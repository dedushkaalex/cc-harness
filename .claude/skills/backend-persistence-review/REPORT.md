# Шаблон отчёта

Справочник к последнему шагу из [SKILL.md](SKILL.md). Блок Scope, затем четыре раздела в этом порядке плюс «Вне scope»; пустой раздел остаётся с пометкой «не найдено», чтобы читатель знал, что проход был. Блок Scope обязателен: следующий агент в pipeline должен видеть не «этого не проверяли», а кто обязан это проверить.

## Лимиты

- Persistence summary — не больше 15 операций и 15 constraints; дальше группируй по механизму и отбирай операции про деньги, необратимые действия и данные, на которые опираются другие записи.
- Findings — не больше 10. Остальное — одним P3 «прочие места того же типа» со списком файл:строка.
- Один сценарий — один finding: race, из-за которого нужен constraint, не записывается дважды как «concurrency» и «constraint»; запись без условия, уязвимая и к параллельному, и к повторному выполнению, — один finding, а не «concurrency» плюс «idempotency».
- «Вне scope» — не больше одной строки на категорию.

## Severity

| Уровень | Когда | Пример |
|---|---|---|
| **P1** | Хранилище может потерять, продублировать или повредить данные, либо нарушается atomicity критической операции: деньги, остатки, необратимые действия, данные, на которые опираются другие записи | списание и зачисление в двух автокоммитах, сбой между ними теряет деньги; два параллельных вызова проходят проверку остатка по одному снимку; код читает колонку, которой нет в миграциях |
| **P2** | Подтверждённая проблема consistency, concurrency, idempotency, query cost или migration compatibility без потери критических данных | повторная доставка webhook создаёт вторую запись платежа в статусе `pending`; страница из 200 заказов делает 200 запросов за позициями; rename колонки одним шагом при rolling deploy |
| **P3** | Риск, который проявится при изменении нагрузки, deployment model или системы: второй экземпляр, рост таблицы, второй writer в то же хранилище | in-memory lock защищает переход статуса, экземпляр пока один, второй записан в планах; offset-пагинация по истории операций, размер таблицы не известен |

Архитектурная неидеальность — нет Repository, SQL в сценарии, ORM-модель совпадает с domain-моделью — severity не повышает и сама по себе не finding.

## Confidence

| Уровень | Когда |
|---|---|
| **high** | сценарий виден в коде от входа до записи; deployment model, источник повтора или объём подтверждены источником из Step 0 |
| **medium** | сценарий виден в коде, но его достижимость опирается на одно допущение без источника: число экземпляров, уровень изоляции, размер таблицы, наличие повторов |
| **low** | сценарий виден не полностью (часть пути в коде вне ревью), либо finding условный и опирается больше чем на одно допущение |

## Findings

### [P1] Короткое название проблемы

- **Persistence operation:** какая запись или чтение, в каком механизме;
  «условный», если finding опирается на перенос из предыдущего отчёта.
- **Evidence:** `path/to/file.ts:42` — что именно там видно; вторая операция
  сценария: `path/to/other.ts:17`; вход: откуда вызывается.

  с объёмом, версия и schema несовместимы.
- **Failure scenario:** операции → порядок или сбой между ними → state
  в хранилище.
- **Why it matters:** последствия этого state для системы и данных.
- **Confidence:** high / medium / low — чем подтверждён сценарий, что
  принято как допущение.
- **Suggested minimal solution:** какое свойство хранилища будет держать
  state; способ реализации — как пример для этого стека.
- **Trade-offs:** что становится дороже; когда лучше оставить как есть.

## Пример заполненного finding

```markdown
### [P1] Параллельные списания проходят проверку остатка по одному снимку

- **Persistence operation:** чтение `accounts.balance` и последующая запись
  нового значения в реляционной базе.
- **Evidence:** `src/billing/withdraw.ts:31` — чтение счёта;
  `src/billing/withdraw.ts:34` — `if (account.balance < amount)`;
  `src/billing/withdraw.ts:40` — запись `balance = account.balance - amount`
  вычисленным в приложении значением, autocommit; вход: `POST /withdrawals`,
  два экземпляра API (k8s/deployment.yaml).
- **Problem:** решение о записи принимается по прочитанному значению, а
  запись не проверяет, что значение с тех пор не изменилось.
- **Failure scenario:** A читает 100, B читает 100, A проходит проверку и
  пишет 40, B проходит проверку и пишет 40 → списано 120, остаток 40.
- **Why it matters:** правило «остаток не отрицательный» защищено на каждом
  пути (Domain summary, Protected invariants), но хранилище его не держит:
  деньги списываются дважды, отчётность расходится с фактом.
- **Confidence:** high — путь виден от входа до записи; параллельность
  подтверждена двумя экземплярами.
- **Suggested minimal solution:** записывать остаток условной операцией в
  самом хранилище — уменьшение на сумму с условием, что текущего остатка
  хватает, и проверка числа изменённых строк. В этом проекте —
  `UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1`;
  в документной базе — обновление с условием на поле, в key-value —
  compare-and-swap или транзакционный скрипт.
- **Trade-offs:** проверка правила переезжает в выражение записи, и ошибка
  предметной области строится по результату «0 строк» — нужен один вызов,
  который это делает (владелец правила — backend-domain-review, если
  появится второй путь); дополнительно CHECK `balance >= 0` закроет
  остальных writers ценой миграции существующих данных.
```
