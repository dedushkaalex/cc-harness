# Backend persistence review

## Primary question

> Что окажется в хранилище, если эта persistence operation выполнится частично, дважды или параллельно с такой же, и во что обходится её чтение?

**Finding принадлежит этому skill**, когда проблема в самой операции записи или чтения, а не в том, где она лежит, кто её знает или существует ли правило: две записи, которые должны быть одним целым, фиксируются по отдельности; два параллельных запроса читают один остаток и оба списывают; повторная доставка сообщения создаёт вторую запись; список из 200 заказов загружает позиции 200 запросами; миграция удаляет колонку, которую ещё читает работающая версия.

**Исправления** в этом skill меняют то, как state пишется и читается: сдвинуть или объединить transaction boundary, добавить constraint хранилища, добавить защиту от параллельной записи, сделать операцию idempotent, изменить форму запроса, разбить миграцию на совместимые шаги, исправить mapping между представлением в хранилище и в приложении. Проверка: если исправление — перенести код в другой компонент, finding у `backend-architecture-review`; убрать import или заменить чужой тип — у `backend-dependency-review`; вызвать владельца правила или создать его — у `backend-domain-review`.

Persistence — любое хранилище state за пределами процесса: SQL, документная или key-value база, object storage, event store, очередь с сохранением, файловая система, кэш, если приложение читает из него как из источника истины. Не предполагай SQL, ORM, Repository, Unit of Work, Active Record или Data Mapper: восстанавливай операции из кода.

## Do NOT evaluate

Владелец — `backend-architecture-review`: лежит ли работа с хранилищем в том компоненте и в том слое; слой компонента — из его таблицы.

Владелец — `backend-dependency-review`: знает ли компонент конкретный ORM, драйвер или тип хранилища; выходит ли persistence-тип или тип ошибки хранилища за границу слоя; нужен ли contract или adapter.

Владелец — `backend-domain-review`: существует ли business rule, кто его владелец, есть ли существующий путь записи в обход проверки, дублирование правил, недопустимые state transitions.

Security (injection, доступ к данным), HTTP/API design, общий error handling (потеря контекста, проглоченные ошибки, что показать клиенту при нарушении constraint), тесты, performance вне persistence (CPU, сериализация, вызовы внешних API) — другие skills, когда появятся; пока такие места уходят в «Вне scope» с названием категории и пометкой «владелец не назначен».

**Правило разделения с domain-review:** там спрашивают, есть ли правило и проходит ли через него каждый путь; здесь — держит ли хранилище правило, когда все пути через него проходят, но операции выполняются параллельно, повторно или частично. Один из путей проверку не делает — там. Проверка есть на каждом пути, а два параллельных запроса проходят её по одному и тому же снимку — здесь.

**Правило разделения с dependency-review:** там — кто знает тип хранилища и во что обойдётся его замена; здесь — совпадает ли смысл значения в хранилище и в приложении. Сценарий возвращает тип ORM — там. Приложение читает `NULL` в колонке как «ещё не оплачен», а другой путь пишет туда `NULL` для «оплата отменена» — здесь.

Примеры на границе:

- controller сам открывает транзакцию и пишет в две таблицы — **не здесь**: где лежит код, решает architecture-review. Здесь оценивается граница транзакции, которая останется после переноса: покрывает ли она обе записи.
- application-сценарий возвращает `Prisma.UserGetPayload` — **не здесь**: dependency-review.
- refund пишет `balance` без проверки, которую делает transfer — **не здесь**: обходной путь, domain-review.
- transfer проверяет остаток и списывает двумя отдельными операциями без общей транзакции и без защиты от параллельного выполнения — **здесь**: правило есть на каждом пути, хранилище его не держит.
- webhook оплаты создаёт запись платежа при каждой доставке, а provider повторяет доставку при таймауте — **здесь**: повторное выполнение создаёт дубликат.
- `amount` хранится числом, и три consumers каждый проверяют `amount > 0` — **не здесь**: domain-review.
- часть чтений возвращает soft-deleted записи, часть нет — **не здесь**, если расходится бизнес-предикат «что считать удалённым»: domain-review. **Здесь**, если расходится представление поля: один путь пишет `NULL`, другой читает его как `false`.
- миграция переименовывает колонку одним шагом, а deploy идёт без остановки старой версии — **здесь**.

Всё замеченное вне scope — одной строкой в разделе «Вне scope» с именем skill-владельца.

## Ключевой вопрос для severity

> Какое неверное состояние окажется в хранилище или какая стоимость возникнет, и при каком сценарии выполнения?

Finding существует только с названным сценарием: конкретные операции, порядок или сбой между ними, и state, который получится. «Нет транзакции» — не сценарий. «Между записью заказа и резервом на складе процесс падает; заказ остаётся без резерва, и job оплаты его подхватит» — сценарий. Стоимость запроса — с оценкой объёма: сколько запросов на один вызов и от чего растёт их число.

## Rule vs evidence

ORM, драйвер, database engine, migration tool и структура папок — только evidence того, какая операция выполняется и где проходит граница. Правило формулируется через свойство persistence: «изменения, атомарные для business operation, имеют общую transaction boundary» — правило; «Prisma query должна быть внутри `$transaction`» — не правило. Поля Problem, Failure scenario и Why it matters пишутся без названий технологий; названия допустимы в Evidence и в Suggested minimal solution как пример реализации. Проверка каждого finding — substitution test из STEPS.md: замени стек на PostgreSQL + Prisma, PostgreSQL + TypeORM, SQLAlchemy, Ecto, Go `database/sql`, SQLx, MongoDB, Redis. Если finding исчезает — его не было; если меняются только evidence и способ исправления — finding настоящий.

## Вход

С отчётами предыдущих skills на входе: таблица компонентов architecture-review — **исходная модель**, из неё берутся те, кто пишет и читает хранилище; Dependency map — стрелки к хранилищу, только дополнение к колонке «использует»; Domain summary — правила, state transitions и то, какие операции должны быть атомарными. Компоненты и правила заново не выводятся. Противоречие с моделью записывается в Mismatches блока Scope с владельцем того skill. Если finding предыдущего skill переносит код или меняет владельца правила, оценивается состояние **после** изменения, finding помечается «при условии применения [P2] architecture-review». Finding предыдущего skill не повторяется: domain-review сообщил, что refund обходит проверку, — здесь оценивается только, держит ли хранилище правило на путях, которые через проверку проходят. Строки «Вне scope» с владельцем `backend-persistence-review` из всех предыдущих отчётов — обязательные кандидаты для Step 2–9: каждая получает вердикт finding, Non-finding или Existing protections. Без отчётов — Step 0 выполняется самостоятельно по STEPS.md, и в блоке Scope это указано.

## Порядок работы

Подробные вопросы для каждого шага — в [STEPS.md](STEPS.md). Шаг закрыт, когда выполнен его критерий.

- [ ] **Step 0 — Code under review и контекст.** Взять из отчётов или собрать по STEPS.md; дособрать deployment model, число экземпляров, источники повторного выполнения, ожидаемые объёмы. Критерий: в блоке Scope названы граница кода под ревью и список «известно / не известно» с источниками.
- [ ] **Step 1 — Persistence model.** Восстанови из кода механизмы хранения, данные, операции, transaction boundaries, связи записей и constraints. Критерий: таблица механизм — данные — операции — где вызываются — граница транзакции; таблица существующих constraints.
- [ ] **Step 2 — Mapping.** Для каждой границы между представлением в хранилище и в приложении проверь совпадение смысла. Критерий: у каждого расхождения названы поле, два смысла и путь, на котором они сталкиваются; естественно совпадающее представление в findings не попало.
- [ ] **Step 3 — Transactions и atomicity.** Найди группы изменений, которые должны выполниться целиком. Критерий: у каждого finding доказаны три пункта — группа существует, частичное выполнение вредно, persistence model такое состояние допускает.
- [ ] **Step 4 — Concurrency.** Найди места, где результат зависит от порядка параллельных операций. Критерий: у каждого finding две конкретные операции, их чередование и итоговый state; механизм защиты не предложен раньше, чем описана проблема.
- [ ] **Step 5 — Constraints.** Сопоставь invariants из Domain summary с constraints хранилища. Критерий: finding только для отсутствующего constraint с persistence-сценарием, в котором хранилище примет недопустимое состояние; существующие constraints записаны в Existing protections.
- [ ] **Step 6 — Query cost.** Найди запросы, чья стоимость не оправдана объёмом или растёт с ним. Критерий: у каждого finding число запросов на вызов или объём данных и от чего они растут; «несколько запросов» без оценки — не finding.
- [ ] **Step 7 — Idempotency.** Для входов, где повторное выполнение ожидается, ответь, что случится при втором выполнении. Критерий: у каждого finding источник повтора и неверное состояние после него.
- [ ] **Step 8 — Failure modes.** Для каждого пути записи проверь сбой между шагами, потерю ответа после commit, rollback с побочными эффектами, stale read. Критерий: у каждого finding точка сбоя и state после неё.
- [ ] **Step 9 — Migrations.** Проверь изменения schema против существующих данных, старой и новой версии кода и deployment model. Критерий: у каждого finding названа несовместимая пара; при stop-the-world deploy одношаговый rename записан в Non-findings.
- [ ] **Step 10 — Recommendations и substitution test.** Минимальное изменение и проверка на смену стека. Критерий: у каждой рекомендации четыре пункта из STEPS.md; в Problem, Failure scenario и Why it matters нет названий технологий.
- [ ] **Отчёт** по шаблону из [REPORT.md](REPORT.md), с блоком Scope.

## Правила для findings

- Каждый finding опирается на конкретный код: путь к файлу и строка каждой операции сценария. Без evidence finding не существует.
- У каждого finding есть **Confidence** — high / medium / low — с основанием: чем подтверждён сценарий (код, deployment model, объёмы, повторы) и что принято как допущение; подробнее в REPORT.md.
- Severity — по последствиям для хранимого state и по стоимости, не по вкусу. P1 — потеря, дублирование или повреждение данных, нарушение критической atomicity. P2 — подтверждённая проблема consistency, concurrency, idempotency, query cost или migration compatibility. P3 — риск, зависящий от нагрузки, deployment model или будущих изменений. Архитектурная неидеальность severity не повышает.
- Отсутствие Repository, Unit of Work, отдельного persistence layer, Active Record, SQL в коде напрямую, ORM-модель, совпадающая с domain-моделью, — не findings. Finding существует только при доказанной проблеме correctness, concurrency, consistency, смысла представления, стоимости запросов или совместимости миграции.
- Рекомендация не выходит за границу skill: «перенести код», «ввести contract», «вызвать владельца правила» — в «Вне scope» с именем владельца.
- Существующие защиты — constraints, transactions, locks, idempotency keys, безопасный порядок миграций — фиксируются так же обязательно, как проблемы: следующий ревьюер должен знать, что трогать не нужно.
