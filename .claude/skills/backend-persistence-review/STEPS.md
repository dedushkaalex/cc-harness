# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага.

## Step 0 — Code under review и контекст

**С `Shared context` от оркестратора `backend-review`** — брать его как Context, не собирать заново, дособирать по правилам ниже только то, чего в нём нет; граница кода под ревью — из него.

**С отчётами на входе** — граница кода под ревью и блок Context берутся из блока Scope отчёта architecture-review. Таблица компонентов даёт список тех, кто пишет и читает хранилище (колонка «использует»). Dependency map даёт стрелки к хранилищу, попавшие в findings dependency-review: только дополнение к колонке «использует». Domain summary даёт таблицу правил и таблицу переходов: из них берутся требования атомарности («заказ и резерв создаются вместе») и state, который хранилище должно держать. Пути записи state, у которого в Domain summary есть правило, берутся из его таблицы правил (колонки «через владельца» и «в обход») без нового поиска по репозиторию.

**Без отчётов** — определи код под ревью сам: diff или названные файлы плюс один шаг по графу вызовов; модуль целиком плюс один шаг наружу; весь репозиторий — только если сказано явно.

**Особенность этого skill.** Параллельный или повторный вызов той же операции редко виден в коде под ревью. Поэтому для state без правила в Domain summary на Step 4 и Step 7 ищутся все входы, которые приводят к той же записи: handler, consumer очереди, webhook, job, CLI, второй сервис с тем же хранилищем. Найденный так модуль **не** становится кодом под ревью: в нём проверяется только одно — пишет ли он тот же state и в каком порядке. Всё остальное в нём не оценивается.

**Контекст, который нужен только этому skill**, в порядке надёжности источников:

1. **Deployment model** — rolling, blue-green, stop-the-world; один экземпляр процесса или несколько. Источники: манифесты (`docker-compose`, k8s, systemd), CI pipeline, README. От этого зависят Step 4 (параллельность между процессами) и Step 9 (совместимость версий).
2. **Источники повторного выполнения** — очереди с at-least-once delivery, retry в клиентах, webhook providers, которые повторяют доставку, jobs по расписанию. Источники: конфигурация очередей, документация provider, retry policy в HTTP-клиентах.
3. **Ожидаемые объёмы** — размер таблиц и коллекций, число позиций в заказе, лимиты пагинации. Источники: документы, seeds, существующие индексы, тесты нагрузки, комментарии в миграциях.
4. **Гарантии хранилища** — engine и версия, уровень изоляции по умолчанию, реплики для чтения, наличие транзакций вообще (документная база, key-value). Источники: конфигурация подключения, миграции, docker-compose.

Итог — список «известно / не известно»:

```text
Известно:    два экземпляра API за балансировщиком — k8s/deployment.yaml, replicas: 2
Известно:    deploy rolling, старая и новая версии живут вместе до минуты — CI, README
Известно:    webhook оплаты повторяется до 5 раз при таймауте — docs/payments.md
Не известно: размер таблицы orders — в источниках нет; допущение: растёт без ограничения
Не известно: уровень изоляции — конфигурации нет; допущение: read committed по умолчанию engine
```

Не ищи дольше одного прохода: нет ответа — «не известно», в finding это допущение с Confidence не выше medium.

## Step 1 — Persistence model

Восстанови из кода, а не из README: какие механизмы хранения существуют и как к ним обращаются. Ищи объекты подключения и клиентов, файлы схемы, миграции, места, где строятся запросы или команды. Не предполагай SQL: хранилищем может быть документная база, key-value, object storage, event store, очередь с сохранением, файловая система, кэш, из которого читают как из источника истины.

Для каждого механизма запиши:

- **данные** — какие сущности, записи, ключи, объекты в нём лежат;
- **операции** — чтения и записи, каждая с файлом и строкой; bulk-операции, upsert, инкременты, условные записи отдельно;
- **где вызываются** — компонент из исходной модели или, без отчёта, модуль;
- **transaction boundary** — где начинается и заканчивается атомарная единица, если механизм её поддерживает: `BEGIN`/`COMMIT`, `$transaction`, `Repo.transaction`, `session.begin`, `BeginTx`, `MULTI`/`EXEC`, session в документной базе; операция без границы записывается как «autocommit»;
- **связи записей** — какие записи ссылаются друг на друга: foreign key, встроенный идентификатор, ключ в key-value, который указывает на строку в другой базе, объект в object storage, на который ссылается запись.

Итог — таблица (лимит 15 строк, дальше группируй по механизму):

| Механизм | Данные | Операция | Где | Transaction boundary |
|---|---|---|---|---|
| PostgreSQL | `orders`, `order_items` | insert order, insert items | `create-order.ts:40-58` | одна транзакция, `create-order.ts:38` |
| PostgreSQL | `inventory` | update stock | `reserve.ts:12` | autocommit, отдельно от заказа |
| Redis | `cart:{userId}` | read, delete | `create-order.ts:30,62` | нет |
| S3 | `invoices/{orderId}.pdf` | put | `invoice.ts:20` | нет |

Вторая таблица — **существующие constraints** хранилища: unique, foreign key, check, not-null, exclusion, TTL, schema validation в документной базе, версия документа. Для каждого — где объявлен (миграция, схема, файл) и какой state он держит. Эта таблица целиком идёт в Existing protections отчёта, кроме constraints, которые объявлены, но не действуют (отключены, deferred без проверки, validation выключена).

## Step 2 — Mapping

Граница mapping — место, где значение переходит между представлением в хранилище и представлением в приложении: чтение строки в структуру, запись структуры в документ, десериализация ключа. Вопрос один: **означает ли значение по обе стороны одно и то же?**

Кандидаты:

- **nullability** — колонка допускает `NULL`, приложение считает поле обязательным, или наоборот; `NULL` означает два разных состояния на двух путях;
- **поля, которые генерирует хранилище** — идентификатор, timestamp, значение по умолчанию, счётчик: приложение использует их до commit, или считает, что задаёт само, а хранилище перезаписывает;
- **точность и тип** — деньги в float, timestamp без зоны при клиентах в разных зонах, целое, которое переполнится, строка с обрезанием по длине;
- **закодированные значения** — enum как строка или число, набор значений в коде не совпадает с набором в хранилище или в старых данных;
- **структурные поля** — JSON-колонка или вложенный документ, форму которых при чтении никто не проверяет, а код рассчитывает на определённые ключи;
- **флаги видимости** — soft delete, архив, версия: чтения по-разному трактуют само поле (`NULL` вместо `false`, версия из другого механизма); если расходится бизнес-предикат «что считать удалённым или активным», это domain-review;
- **одно поле, два смысла** — `status` в хранилище хранит стадию, а код где-то читает из него признак оплаты.

Finding — только с путём, на котором расхождение сталкивается: запись со смыслом A на `a.ts:12`, чтение со смыслом B на `b.ts:30`, что получает пользователь. Если представления совпадают естественно — ORM-модель и есть модель приложения, и никаких расхождений нет — это не finding и не повод требовать отдельный слой mapping.

**Разделение с dependency-review:** если проблема в том, что тип хранилища виден в другом слое и его замена дорога, — там. Если проблема в том, что значение означает разное, — здесь, каким бы типом оно ни было представлено.

**Разделение с domain-review:** расходится то, что означает значение хранилища (`NULL`, default, кодировка, форма документа), — здесь; часть путей применяет бизнес-предикат, а часть нет — дублирование или обход, domain-review.

## Step 3 — Transactions и atomicity

Группа связанных изменений — несколько записей, которые для business operation составляют одно целое: создать заказ, зарезервировать товар, создать запись оплаты; списать с одного счёта и зачислить на другой; записать событие и обновить проекцию. Источники: Domain summary (правила, которые связывают несколько записей), код (одна операция пишет в два места), тесты.

Для каждой группы три доказательства, без любого из них finding нет:

1. **Группа существует** — назови записи и правило или сценарий, который делает их одним целым.
2. **Частичное выполнение вредно** — назови state после сбоя между записями: «заказ есть, резерва нет, job оплаты его подхватит»; «резерв есть, заказа нет, товар заблокирован навсегда». Если частичное состояние безвредно или исправляется следующим шагом — не finding.
3. **Persistence model это допускает** — границы транзакции нет, она покрывает часть группы, записи идут в разные механизмы без общей транзакции (база и очередь, база и object storage, две базы), или транзакция открывается, но одна из записей делается другим подключением.

Отдельные случаи:

- **Разные механизмы.** Общая транзакция невозможна по построению; finding существует, только если нет компенсации: outbox, идемпотентный consumer, сверка, порядок «сначала необратимое, потом ссылка на него». Наличие такой компенсации — запись в Existing protections.
- **Слишком широкая транзакция.** Не finding по факту; finding, если внутри границы есть ожидание внешней системы (HTTP-вызов, отправка письма) и это держит блокировки или соединение — с оценкой, что именно заблокировано.
- **Транзакция, которая не делает того, что кажется.** Вложенная транзакция, которая на самом деле присоединяется к внешней; транзакция, объявленная на уровне выше, но операция использует другой клиент или пул. Это evidence для пункта 3.

Итог — по одной строке на группу: записи, граница, вердикт «атомарна / частичное состояние возможно», сценарий сбоя.

## Step 4 — Concurrency

Ищи операции, результат которых зависит от порядка выполнения двух одинаковых или пересекающихся вызовов. Типовые формы:

- **read → check → write** — прочитать остаток, сравнить, записать новое значение; прочитать счётчик, увеличить в приложении, записать;
- **check exists → insert** — проверить, что записи нет, и создать; два вызова оба не находят и оба создают;
- **переход статуса без условия** — прочитать `pending`, записать `paid`; параллельный вызов делает то же, и оплата обрабатывается дважды;
- **предположение об одном процессе** — in-memory lock, флаг в памяти, «очередь обрабатывает по одному», при нескольких экземплярах из Step 0;
- **чтение из реплики или кэша перед записью** — решение принимается по устаревшему значению.

Для каждого кандидата опиши сценарий **до** любого разговора о механизме защиты: два вызова A и B, чередование их шагов, итоговый state. «A читает 100, B читает 100, A пишет 40, B пишет 40 — списано 120, остаток 40». Без чередования и итога finding нет.

Затем проверь, нет ли уже защиты, и запиши её в Existing protections: условная запись (`WHERE status = 'pending'`, `UPDATE ... SET balance = balance - ?` с проверкой в том же выражении, `findOneAndUpdate` с условием, `SET NX`, compare-and-swap по версии документа), атомарный инкремент в хранилище, unique constraint, который делает вторую вставку ошибкой, блокировка строки, optimistic version, уровень изоляции serializable с обработкой повтора, единственный consumer очереди по ключу, advisory lock, транзакционный скрипт в key-value. Механизм называется по его свойству — «условная запись», «блокировка», «версия» — а не по API конкретного стека.

Не предлагай `SELECT ... FOR UPDATE`, optimistic lock или serializable раньше, чем описана проблема: выбор механизма — Step 10, и он зависит от нагрузки и от того, что дешевле в этом хранилище.

## Step 5 — Constraints

Возьми invariants из Domain summary, которые касаются целостности хранимого state: уникальность (`один активный подписчик на email`), ссылочная целостность (позиция ссылается на существующий заказ), допустимый диапазон (`balance >= 0`), обязательность, взаимоисключение (два бронирования не пересекаются по времени). Сопоставь с таблицей constraints из Step 1.

Для invariant без constraint finding есть только при **persistence-сценарии**, в котором хранилище примет недопустимое состояние, хотя приложение проверяет правило на каждом пути:

- два параллельных вызова проходят проверку по одному снимку (Step 4) — тогда это один finding с причиной «constraint отсутствует», а не два;
- частичный commit оставляет ссылку на несуществующую запись (Step 3);
- в то же хранилище пишет кто-то, кроме кода под ревью: второй сервис, job, миграция данных, ручной доступ — с источником из Step 0; путь, который Domain summary уже записал в колонке «в обход», сюда не входит: constraint для него предлагается только по handoff из Trade-offs domain-review, одним условным finding;
- domain-review в своём отчёте передал сюда «при третьем канале записи стоит добавить constraint».

Если приложение проверяет правило на всех путях и ни одного такого сценария нет — Non-findings с причиной, не finding «а вдруг». Если constraint есть и приложение проверяет тоже — это не дублирование: проверка в приложении даёт понятный ответ пользователю, constraint держит целостность; обе записываются в Existing protections. Что приложение отдаёт при нарушении constraint — «Вне scope», владелец `backend-error-handling-review`.

Constraint, который объявлен, но не действует: отключённая проверка, validation в документной базе в режиме предупреждения, foreign key без индекса на большой таблице (стоимость — Step 6), deferred constraint без проверки на commit. Записывается как finding, если на него рассчитывает Existing protections.

## Step 6 — Query cost

Только стоимость обращений к хранилищу; CPU, сериализация и вызовы внешних API — не здесь. Кандидаты:

- **N+1** — запрос внутри цикла по результатам другого запроса: список заказов, затем позиции для каждого; ленивая загрузка связи в цикле;
- **повторение одного запроса** внутри одной операции — тот же объект читается трижды разными функциями; кроме стоимости это даёт разные снимки одного state (Step 8);
- **полная загрузка с фильтрацией в памяти** — прочитать всё и отфильтровать, отсортировать или посчитать в приложении;
- **лишние данные** — все колонки или весь документ там, где нужны два поля, только если объём значим: большие JSON, blob, вложенные коллекции;
- **пагинация** — offset на растущем наборе, `count(*)` при каждом запросе страницы, выборка всей страницы ради `exists`;
- **фильтр без индекса** — запрос по колонке, у которой нет индекса, на таблице, размер которой известен или разумно ожидается большим;
- **рост с объёмом** — запрос, который сейчас дёшев, но растёт линейно с полем, у которого нет верхней границы: позиции заказа ограничены, история операций — нет.

Finding нужен evidence стоимости: число запросов на один вызов и от чего оно растёт («200 запросов на страницу из 200 заказов»), или объём данных с источником из Step 0, или допущение с Confidence не выше medium. Несколько запросов в одной операции, чтение из небольшой ограниченной таблицы (справочник, настройки), запрос без индекса на таблице в сотню строк — Non-findings с причиной.

Запись в Existing protections: batch-загрузка связей, проекция нужных полей, keyset-пагинация, индексы под существующие запросы.

## Step 7 — Idempotency

Входы, где повторное выполнение ожидается, — из Step 0: consumer очереди с at-least-once delivery, webhook, retry в клиенте, job по расписанию, который может запуститься дважды при нескольких экземплярах, повторная отправка формы, если это подтверждено. Для каждого входа пройди путь до записей и ответь: **что окажется в хранилище после второго выполнения с теми же данными?**

- вставка без естественного ключа — вторая запись: два платежа, два письма в outbox;
- инкремент — двойной счёт;
- переход статуса без условия — повторная обработка: вторая отгрузка, второй возврат;
- запись плюс внешнее действие — действие повторяется, даже если запись не изменилась;
- перезапись тем же значением, условная запись, upsert по ключу — безопасно, Existing protections.

Finding только если второе выполнение создаёт неверное состояние **и** повтор ожидается. Для consumer очереди, webhook и job при нескольких экземплярах повтор принимается по умолчанию и без источника: допущение, Confidence не выше medium. Для retry в HTTP-клиенте и повторной отправки формы нужен источник из Step 0; без него — Non-findings с причиной «повтор только в теории». Не требуй идемпотентности от каждой записи. Если та же запись уже записана как finding на Step 4 или Step 5, второй finding не создаётся: источник повтора добавляется в Evidence того же finding.

Существующие защиты: ключ идемпотентности, сохранённый с unique constraint; таблица обработанных сообщений; условная запись по статусу; upsert по естественному ключу; версия документа. Записываются в Existing protections с указанием, что именно ключ покрывает: ключ на уровне запроса не защищает от повторного запуска job.

## Step 8 — Failure modes

Для каждого пути записи из Step 1 пройди точки сбоя. Не оценивай, как ошибка обрабатывается и логируется, — только что остаётся в хранилище:

- **сбой между шагами** — процесс падает после записи A до записи B: это Step 3, здесь не повторяется;
- **потеря ответа после commit** — запись зафиксирована, клиент получил таймаут и повторит: это вход для Step 7, здесь не повторяется, если там учтён;
- **rollback с побочными эффектами** — транзакция откатилась, а письмо отправлено, сообщение опубликовано, файл загружен в object storage, кэш обновлён; state хранилища и внешний мир расходятся;
- **побочный эффект внутри транзакции по данным, которых ещё нет** — публикация события с идентификатором до commit; consumer приходит раньше, чем запись видна;
- **stale read** — чтение из реплики, кэша или второго запроса того же state, по которому принимается решение о записи; чтение после записи в той же операции, которое не видит собственную запись;
- **кэш как часть persistence semantics** — если приложение читает из кэша как из источника истины: порядок «обновить базу, обновить кэш» и что будет при сбое между ними; инвалидация, которую пропускает один из путей записи.

Finding — с точкой сбоя и state после неё. Стоит ли повторять операцию, что сообщено вызывающему о сбое и обработка исключений как таковая — «Вне scope», владелец `backend-error-handling-review`.

## Step 9 — Migrations

Только если код под ревью меняет schema, добавляет миграцию или использует поле, для которого миграции нет. Совместимость проверяется по четырём парам:

| Пара | Вопрос |
|---|---|
| существующие данные → новая schema | примет ли новый constraint или тип старые строки: `NOT NULL` без default, сужение типа, новый unique при дубликатах |
| старая версия кода → новая schema | читает ли старая версия колонку, которую переименовали или удалили; пишет ли в неё |
| новая версия кода → старая schema | ждёт ли новая версия колонку, которой ещё нет, пока миграция не применена |
| порядок миграций | зависят ли миграции друг от друга, применяются ли в транзакции, есть ли backfill большой таблицы под блокировкой |

Опасные формы: rename и drop одним шагом, смена nullability, смена смысла поля без переименования, деструктивная миграция данных без обратного пути, несовместимая смена типа, backfill в той же транзакции, что и изменение schema, на таблице известного большого размера.

Deployment model из Step 0 решает вердикт. Rolling deploy, несколько экземпляров — старая и новая версии живут вместе, и rename одним шагом ломает одну из них: finding. Stop-the-world, один экземпляр, миграция перед стартом — тот же rename безопасен: Non-findings с причиной. Zero-downtime не требуется по умолчанию; Confidence не выше medium, если deployment model — допущение.

Поле используется в коде, а миграции нет, или миграция есть, а код читает поле по старому имени — P1 независимо от deployment model.

## Step 10 — Recommendations и substitution test

Для каждого finding — минимальное изменение, порядок от дешёвого к дорогому:

1. условная запись или атомарная операция в самом хранилище вместо read → check → write;
2. constraint хранилища: unique, check, foreign key, exclusion, schema validation;
3. расширить или сдвинуть transaction boundary, чтобы она покрыла группу;
4. ключ идемпотентности с unique constraint или таблица обработанных сообщений;
5. блокировка или версия для сценариев, где условная запись не выражает правило;
6. форма запроса: batch-загрузка связей, проекция, keyset-пагинация, индекс;
7. разбить миграцию на совместимые шаги: добавить, переключить код, удалить;
8. outbox, сверка или порядок операций для записей в разные механизмы.

Repository, Unit of Work, отдельный persistence layer, смена ORM или движка ради чистоты не предлагаются. Новая abstraction оправдана только сценарием из finding, который она закрывает.

К каждой рекомендации четыре пункта:

1. **Какая persistence problem существует** — ссылка на evidence.
2. **Как она возникает** — операции, порядок или сбой, state.
3. **Как изменение её устраняет** — какое свойство хранилища теперь держит state.
4. **Какую стоимость добавляет** — блокировки под нагрузкой, повторы при конфликте версий, миграция существующих данных, дополнительная таблица, ещё один шаг deploy.

Если изменение дороже проблемы — «оставить как есть», источник из Context и при каком изменении вердикт поменяется: «при втором экземпляре», «при росте таблицы», «при переходе на rolling deploy».

**Substitution test** для каждого finding перед записью в отчёт. Перепиши Problem, Failure scenario и Why it matters без названий ORM, драйвера, движка, migration tool и папок. Представь то же хранилище state на другом стеке — как минимум на трёх из: PostgreSQL + Prisma, PostgreSQL + TypeORM, Python + SQLAlchemy, Elixir + Ecto, Go + `database/sql`, Rust + SQLx, MongoDB, Redis. Если finding исчезает — его не было: «query не внутри `$transaction`», «нет Repository», «entity совпадает с domain-моделью» — не findings. Если меняются только Evidence, API и способ реализации в Suggested minimal solution — finding настоящий: race read → check → write существует в любом хранилище, а условная запись выражается в SQL через `WHERE`, в документной базе через условие обновления, в key-value через compare-and-swap. Не требуй, чтобы пример работал во всех восьми стеках: проверяется reasoning, а не синтаксис.
