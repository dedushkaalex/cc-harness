# Шаблон отчёта

Справочник к последнему шагу из [SKILL.md](SKILL.md). Блок Scope, затем три раздела в этом порядке плюс «Вне scope»; пустой раздел остаётся с пометкой «не найдено», чтобы читатель знал, что проход был. Блок Scope обязателен: следующий агент в pipeline должен видеть не «этого не проверяли», а кто обязан это проверить.

## Severity

| Уровень | Когда | Пример |
|---|---|---|
| **P1** | Смешение видов работы или код не в своём слое блокирует изменение: добавить сценарий, транспорт или хранилище нельзя без копирования или переписывания чужого кода | handler читает запрос, проверяет бизнес-правила и пишет в БД одной функцией; очередь для импорта заказов потребует скопировать всё это |
| **P2** | Заметная проблема maintainability: изменение возможно, но дороже, чем должно быть, и риск ошибок растёт | controller сам открывает транзакцию и пишет в две таблицы в обход существующего сценария |
| **P3** | Потенциальная проблема, вердикт зависит от контекста, который из кода не виден | repository содержит одно бизнес-правило («просроченный заказ не возвращать»); станет проблемой, когда правило понадобится второму месту |

Стилистическое предпочтение («я бы назвал слой иначе», «мне ближе другая структура папок») — не finding. Максимум P3, и только если можно назвать изменение, которое станет дороже.

## Структура

```markdown
## Scope

Evaluated:
- responsibilities: какие виды работы выполняет каждый компонент
- placement of work: код какого слоя лежит в каждом компоненте

Not evaluated:
- dependency direction, coupling, leakage, cycles, abstractions
  Owner: `backend-dependency-review`
- SQL, performance, security, error handling, tests, naming
  Owner: соответствующие skills

## Architecture summary

Три–шесть предложений: какие слои реально существуют, где живут transport,
application/business logic и infrastructure, какой компонент что использует.
Описание того, что есть, а не того, каким стилем это должно быть. Факты
использования («`SessionService` использует Redis для сессий») здесь
фиксируются, но не оцениваются.

Таблица компонентов из Step 1 — целиком: это входная модель для
`backend-dependency-review`.

## Findings

### [P1] Короткое название проблемы

- **Problem:** одна фраза, какие виды работы смешаны или код какого слоя
  лежит не на месте.
- **Evidence:** `path/to/file.ts:42` — что именно там видно; при необходимости
  ещё одно–два места.
- **Why it matters:** какое изменение станет дорогим и почему.
- **Suggested solution:** куда переносится код; без новых abstraction.
- **Trade-offs:** что становится хуже после переноса; когда лучше оставить
  как есть.

### [P2] ...

## Good decisions

- `path/to/file.ts` — какое разделение видов работы или какая граница
  уже держится и почему это стоит сохранить.

## Вне scope

Одна строка на замеченное, с именем skill-владельца:
«`src/orders/order.service.ts:12` — после переноса транзакции сервис будет
использовать Prisma напрямую; оценка стрелки — backend-dependency-review».
«`x.ts:12` — SQL-строка склеивается вручную — security/SQL review».
```

## Пример заполненного finding

```markdown
### [P2] Controller управляет транзакцией и обращается к ORM напрямую

- **Problem:** `OrderController` совмещает transport и persistence:
  парсит запрос, открывает транзакцию Prisma и пишет в две таблицы.
- **Evidence:** `src/http/order.controller.ts:31-58` — `prisma.$transaction`
  внутри handler; `OrderService` при этом существует, но вызывается только
  для расчёта суммы.
- **Why it matters:** добавить второй transport (очередь для импорта
  заказов) нельзя без копирования транзакционной логики.
- **Suggested solution:** перенести транзакцию и запись в
  `OrderService.create`, оставить controller только разбор запроса
  и вызов сервиса.
- **Trade-offs:** `OrderService` вырастет и начнёт использовать Prisma
  напрямую. Нужна ли для этой стрелки abstraction — вопрос
  `backend-dependency-review`, здесь не оценивается.
```
