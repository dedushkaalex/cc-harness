# Backend architecture review

## Зона ответственности

Ровно четыре вопроса к коду:

1. **Responsibilities** — не смешивает ли один компонент разные виды работы.
2. **Boundaries** — не протекают ли transport, business logic и infrastructure друг в друга.
3. **Dependencies** — в ту ли сторону направлены зависимости и все ли они необходимы.
4. **Coupling** — какие зависимости делают замену технологии или компонента дорогой.

SQL, индексы, performance, security, корректность auth, error handling, тесты, naming, форматирование, TypeScript style, framework best practices и «правильность паттернов» проверяют другие skills. Заметил такое — упомяни одной строкой в конце отчёта как «вне scope», без finding.

## Ключевой вопрос

> Какое изменение в системе станет дорогим из-за текущего дизайна?

Finding существует только тогда, когда на этот вопрос есть конкретный ответ: «замена Redis на Memcached потребует править три application service». Паттерн, interface или port — это возможный ответ на уже найденную проблему, а не то, что ты ищешь. Решение без названной проблемы в отчёт не попадает.

## Порядок работы

Подробные вопросы для каждого шага — в [STEPS.md](STEPS.md). Шаг закрыт, когда выполнен его критерий.

- [ ] **Step 1 — Reconstruct.** Восстанови архитектуру из кода, а не из README и не из знакомого стиля (Clean, Hexagonal, MVC). Критерий: таблица всех компонентов в scope с колонками «ответственность», «от кого зависит», «слой: transport / application / domain / infrastructure».
- [ ] **Step 2 — Responsibilities.** Для каждого компонента из таблицы перечисли виды работы, которые он делает. Критерий: у каждого компонента есть список; в findings уходят только те, где смешаны *разные виды* работы, а не просто много методов.
- [ ] **Step 3 — Boundaries.** Отметь существующие границы и каждое место, где деталь одного слоя видна в другом. Критерий: для каждого пересечения границы названы файл и строка.
- [ ] **Step 4 — Dependencies.** Построй граф зависимостей из таблицы. Критерий: для каждой подозрительной стрелки дан ответ на четыре вопроса — кто от кого, необходима ли, implementation detail ли, создаёт ли coupling.
- [ ] **Step 5 — Coupling.** Для каждой оставшейся стрелки оцени стоимость замены её цели. Критерий: у каждой есть вердикт «дорого / приемлемо в этом контексте» с обоснованием.
- [ ] **Step 6 — Recommendations.** Для каждой проблемы — минимальное изменение. Критерий: у каждой рекомендации названы решаемая проблема, добавляемая стоимость и почему она оправдана именно здесь. Если abstraction не нужна, так и написано.
- [ ] **Overengineering pass.** Пройди все существующие interface, abstract class, generic-обёртки и слои-прослойки по критериям из [OVERENGINEERING.md](OVERENGINEERING.md). Критерий: у каждой abstraction есть вердикт «оправдана / лишняя» с причиной.
- [ ] **Отчёт** по шаблону из [REPORT.md](REPORT.md).

## Правила для findings

- Каждый finding опирается на конкретный код: путь к файлу и строка. Без evidence finding не существует.
- Severity — по стоимости изменений, не по вкусу. P1 — существенный coupling или блокировка изменений. P2 — заметная проблема maintainability. P3 — зависит от контекста. Стилистическое предпочтение — максимум P3, обычно вообще не finding.
- `Application Service → Redis` и подобные прямые зависимости от инфраструктуры — повод для оценки, не автоматический finding. Вердикт зависит от числа consumers, вероятности замены и стоимости обёртки.
- Хорошие решения фиксируются так же обязательно, как проблемы: следующий ревьюер должен знать, что трогать не нужно.
