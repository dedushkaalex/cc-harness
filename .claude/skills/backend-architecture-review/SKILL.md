# Backend architecture review

## Primary question

> Какой вид работы выполняется здесь, и должен ли он лежать в этом компоненте?

**Finding принадлежит этому skill**, когда проблема вызвана тем, что внутри компонента лежит не тот вид работы: код persistence в transport, бизнес-правило в repository, формирование HTTP-ответа в сценарии, смешение трёх видов работы в одном компоненте.

**Исправления** в этом skill — перенос кода между компонентами: переместить, выделить в существующий компонент правильного слоя, разбить компонент на два. Проверка: если исправление — убрать import, сменить тип, перевернуть стрелку или ввести interface, finding не отсюда.

## Do NOT evaluate

Владелец всех пунктов ниже — `backend-dependency-review`:

- импорты и то, что компонент знает о других компонентах;
- направление зависимостей;
- coupling и стоимость замены технологии;
- leakage типов, ошибок, DTO через границы слоёв;
- зависимости от конкретного SDK, ORM, драйвера;
- interface / port / adapter / dependency inversion — нужны они или лишние.

SQL, индексы, performance, security, корректность auth, error handling, тесты, naming, style — другие skills, когда появятся; пока такие места уходят в «Вне scope» с названием категории и пометкой «владелец не назначен».

Всё, через что компонент получает другие компоненты (импорты, параметры конструкторов и функций, объявленные требования, глобальные объекты), **собирается** на Step 1 в колонку «использует»: это данные для следующего skill. Собирать нужно, оценивать нельзя. «`SessionService` использует Redis для хранения сессий» — факт в карте. «`SessionService` напрямую зависит от Redis» — finding, которого в этом отчёте нет.

Примеры на границе:

- controller, внутри которого написана транзакция и запись в две таблицы — **здесь**: код persistence лежит в transport.
- application service возвращает тип `Prisma.UserGetPayload` — **не здесь**: код на месте, чужой только тип.
- компонент с persistence mapping (`@Entity`, `use Ecto.Schema`, сгенерированная структура) и правилами предметной области внутри — **здесь**, владелец один: это смешение видов работы. Рекомендация вынести правила в отдельный тип даётся, только если Step 0 показывает изменение, которое это удешевит; если проект намеренно держит правила и mapping вместе, это факт для Architecture summary. Стрелку `Domain → ORM` у того, что останется после выноса, оценивает dependency-review.

Всё замеченное вне scope — одной строкой в разделе «Вне scope» с именем skill-владельца, чтобы следующий skill в pipeline это подобрал.

## Ключевой вопрос для severity

> Какое изменение в системе станет дорогим из-за того, что этот код лежит здесь?

Finding существует только тогда, когда на этот вопрос есть конкретный ответ: «добавить второй transport нельзя без копирования транзакционной логики из controller». Если кажется, что без interface или port не обойтись, это признак dependency-проблемы, и она уходит в «Вне scope».

## Порядок работы

Подробные вопросы для каждого шага — в [STEPS.md](STEPS.md). Шаг закрыт, когда выполнен его критерий.

- [ ] **Step 0 — Code under review и контекст.** Определи, какой код проверяется, и собери сведения о планируемых изменениях из источников, перечисленных в STEPS.md. Критерий: в отчёте названы граница кода под ревью, список того, что планируется или не планируется, с источником каждого утверждения, и строка «базовая единица: механизм, источник»; чего в источниках нет — записано как допущение.
- [ ] **Step 1 — Reconstruct.** Восстанови структуру из кода, а не из README и не из знакомого стиля (Clean, Hexagonal, MVC). Критерий: таблица компонентов кода под ревью с колонками «ответственность», «слой» из шести — transport / application / domain / infrastructure / persistence / external service — и «использует».
- [ ] **Step 2 — Responsibilities.** Для каждого компонента из таблицы перечисли виды работы, которые он делает. Критерий: у каждого компонента есть список; в findings уходят только те, где смешаны *разные виды* работы, а не просто много методов.
- [ ] **Step 3 — Boundaries.** Для каждого компонента отметь код, который делает работу другого слоя. Критерий: для каждого такого места названы файл, строка и слой, которому код принадлежит; место, уже записанное на Step 2, здесь не повторяется.
- [ ] **Step 4 — Recommendations.** Для каждой проблемы — минимальное перемещение кода. Критерий: у каждой рекомендации названы решаемая проблема, куда переносится код и что становится хуже. Рекомендация не выходит за границу skill: никаких interface, port, adapter.
- [ ] **Отчёт** по шаблону из [REPORT.md](REPORT.md), с блоком Scope.

## Правила для findings

- Каждый finding опирается на конкретный код: путь к файлу и строка. Без evidence finding не существует.
- У каждого finding есть **Confidence** — high / medium / low — и основание: что из контекста Step 0 подтверждает вердикт, а что принято как допущение. Вердикт «оставить как есть, второй transport не планируется» без источника получает не выше medium.
- Severity — по стоимости изменений, не по вкусу. P1 — смешение блокирует изменение. P2 — заметная проблема maintainability. P3 — зависит от контекста. Стилистическое предпочтение — максимум P3, обычно вообще не finding.
- Много методов одного вида — не finding. Класс с двадцатью запросами к БД — нормальный repository.
- Хорошие решения фиксируются так же обязательно, как проблемы: следующий ревьюер должен знать, что трогать не нужно.
