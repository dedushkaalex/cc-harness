# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага.

## Step 1 — Reconstruct

Цель — описать систему такой, какая она есть в коде. Название папки `domain/` или `usecases/` ещё ничего не доказывает: смотри, что делает файл и с чем работает напрямую.

Определи для каждого компонента (класс, модуль, функция верхнего уровня):

- **Слой** по тому, с чем компонент работает напрямую:
  - transport — HTTP/gRPC/queue handlers, request/response DTO, middleware, routing;
  - application — сценарии использования, оркестрация, транзакционные границы;
  - domain — правила предметной области, инварианты, вычисления без I/O;
  - infrastructure — БД, кэш, очереди, файловая система, внешние API, framework-специфика.
- **Ответственность** одной фразой: «принимает HTTP-запрос на создание заказа и вызывает сценарий».
- **Использует**: прямые импорты, конструкторные параметры, глобальные объекты. Это факт для карты, а не предмет оценки — стрелки оценивает `backend-dependency-review`.

Итог шага — таблица:

| Компонент | Слой | Ответственность | Использует |
|---|---|---|---|
| `OrderController` | transport | принимает запросы на заказы | `OrderService`, `PrismaClient` |

Строка `OrderController` использует `PrismaClient` — это подсказка для Step 3: посмотреть, не лежит ли в controller код persistence. Сама стрелка в finding не превращается.

## Step 2 — Responsibilities

Ищи **смешение видов работы**, а не объём. Класс с двадцатью методами одного вида (двадцать запросов к БД в repository) — норма. Класс с тремя методами трёх видов — кандидат в findings.

Признаки смешения по типам компонентов:

- **Controller** парсит запрос *и* принимает бизнес-решение (проверяет баланс, считает скидку) *и* сам ходит в БД.
- **Application service** оркестрирует сценарий *и* формирует HTTP-ответ или знает про status codes.
- **Domain object** содержит инварианты *и* сериализацию в формат БД или вызовы внешних API.
- **Repository** читает и пишет данные *и* принимает бизнес-решения («если заказ просрочен — отменить»).
- **External API client** делает вызов *и* решает, что делать с бизнес-результатом.
- **Infrastructure service** (mailer, cache, queue) содержит правила предметной области.

Для каждого компонента ответь: если завтра поменяется только транспорт / только хранилище / только бизнес-правило, придётся ли править этот файл? Файл, который правится по трём разным причинам, смешивает три ответственности.

## Step 3 — Boundaries

Граница держится, когда в компоненте лежит код только его слоя. Вопрос к каждому компоненту: **работу какого слоя выполняет этот код?** Если ответ не совпадает со слоем компонента из таблицы Step 1 — это место в findings.

Типовые случаи:

1. **Persistence в transport.** Handler строит запросы, открывает транзакцию, пишет в таблицы.
2. **Бизнес-правила в infrastructure.** Repository, cache-сервис или API client решают, что делать с результатом по правилам предметной области.
3. **Transport в application.** Сценарий формирует status code, заголовки, форму HTTP-ответа.
4. **I/O в domain.** Domain-объект сам ходит в БД или во внешний API.
5. **Всё в одном файле.** Handler читает тело запроса, проверяет правила и пишет в БД одной функцией.

Что сюда **не** входит: чужой тип в сигнатуре, чужой import, чужая ошибка, пробрасываемая наверх. Код при этом лежит на месте, протекло только знание — это leakage, его оценивает `backend-dependency-review`. Проверка: если исправление — перенести строки кода в другой файл, это здесь; если исправление — сменить тип или убрать import, это там.

Для каждого места зафиксируй файл, строку и слой, которому код принадлежит. Отдельно отметь границы, которые **уже держатся**: они пойдут в раздел «Good decisions».

## Step 4 — Recommendations

Для каждого finding предложи **минимальное перемещение кода**, которое снимает названную стоимость. Порядок предпочтений от дешёвого к дорогому:

1. Переместить код в существующий компонент правильного слоя.
2. Выделить функцию или модуль в правильном слое, если подходящего компонента нет.
3. Разбить компонент на два по видам работы.

Новых interface, port, adapter и слоёв-прослоек этот skill не предлагает. Если перемещение кода создаёт стрелку, которую хочется обернуть в abstraction («после переноса `OrderService` будет знать Prisma напрямую»), зафиксируй стрелку в «Вне scope» для `backend-dependency-review` и не оценивай её.

К каждой рекомендации обязательно три пункта:

1. **Какую проблему решает** — со ссылкой на evidence finding.
2. **Куда переносится код** — компонент и слой.
3. **Что становится хуже** — новый файл, длиннее вызов, компонент растёт.

Если перемещение дороже проблемы — напиши прямо: «оставить как есть», и объясни, при каком изменении контекста вердикт поменяется.
