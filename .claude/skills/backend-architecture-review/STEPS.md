# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага.

## Step 1 — Reconstruct

Цель — описать систему такой, какая она есть в коде. Название папки `domain/` или `usecases/` ещё ничего не доказывает: смотри, что импортирует файл и кто импортирует его.

Определи для каждого компонента (класс, модуль, функция верхнего уровня):

- **Слой** по тому, с чем компонент работает напрямую:
  - transport — HTTP/gRPC/queue handlers, request/response DTO, middleware, routing;
  - application — сценарии использования, оркестрация, транзакционные границы;
  - domain — правила предметной области, инварианты, вычисления без I/O;
  - infrastructure — БД, кэш, очереди, файловая система, внешние API, framework-специфика.
- **Ответственность** одной фразой: «принимает HTTP-запрос на создание заказа и вызывает сценарий».
- **Зависимости**: прямые импорты, конструкторные параметры, глобальные объекты, singletons, декораторы framework.

Итог шага — таблица:

| Компонент | Слой | Ответственность | Зависит от |
|---|---|---|---|
| `OrderController` | transport | принимает запросы на заказы | `OrderService`, `PrismaClient` |

Строка `OrderController → PrismaClient` в такой таблице уже сама подсказывает, куда смотреть на Step 3.

## Step 2 — Responsibilities

Ищи **смешение видов работы**, а не объём. Класс с двадцатью методами одного вида (двадцать запросов к БД в repository) — норма. Класс с тремя методами трёх видов — кандидат в findings.

Признаки смешения по типам компонентов:

- **Controller** парсит запрос *и* принимает бизнес-решение (проверяет баланс, считает скидку) *и* сам ходит в БД.
- **Application service** оркестрирует сценарий *и* формирует HTTP-ответ или знает про status codes.
- **Domain object** содержит инварианты *и* сериализацию в формат БД или вызовы внешних API.
- **Repository** читает и пишет данные *и* принимает бизнес-решения («если заказ просрочен — отменить»).
- **External API client** делает вызов *и* решает, что делать с бизнес-результатом.
- **Infrastructure service** (mailer, cache, queue) содержит правила предметной области.

Для каждого компонента ответь: если завтра поменяется только транспорт / только хранилище / только бизнес-правило, придётся ли править этот файл? Файл, который правится по трём разным причинам, смешивает три ответственности.

## Step 3 — Boundaries

Граница — место, где один слой перестаёт знать о деталях другого. Проверь четыре типовых протечки:

1. **Infrastructure → application/domain.** В сценарии или domain-объекте видны типы ORM, SQL-строки, ключи Redis, формат ответа стороннего API.
2. **Controller знает о persistence.** Handler напрямую вызывает ORM, строит запросы, управляет транзакцией.
3. **Domain зависит от framework или БД.** Domain-класс наследует базовую сущность ORM, помечен декораторами framework, импортирует http-модуль.
4. **Всё в одном файле.** Handler читает тело запроса, проверяет правила и пишет в БД одной функцией.

Для каждой протечки зафиксируй файл и строку. Отдельно отметь границы, которые **уже держатся**: они пойдут в раздел «Good decisions».

## Step 4 — Dependencies

Из таблицы Step 1 построй граф: стрелка от того, кто импортирует, к тому, что импортируется. Направление «правильное», когда более стабильные и более абстрактные вещи (правила предметной области) не зависят от более изменчивых (конкретная БД, конкретный transport).

Подозрительная стрелка — любая из:

- domain → infrastructure или domain → transport;
- application → конкретный transport;
- два компонента одного слоя зависят друг от друга по кругу;
- компонент зависит от чужого implementation detail (внутренняя таблица другого модуля, приватный формат кэша).

Для каждой подозрительной стрелки ответь письменно:

1. **Кто зависит от кого.** Именно компоненты, не слои.
2. **Необходима ли зависимость.** Можно ли получить то же поведение, передав данные параметром или вернув результат наверх?
3. **Implementation detail ли это.** Зависит ли компонент от *того, что* делает цель, или от *того, как* она это делает (конкретный SDK, схема таблицы, формат ключа)?
4. **Создаёт ли coupling.** Что придётся править, если цель заменить?

## Step 5 — Coupling

Coupling измеряется стоимостью замены. Возьми каждую стрелку в infrastructure и спроси: «если заменить цель на аналог, сколько файлов придётся править и насколько разбросаны правки?»

Пример: `Application Service → Redis`.

- Один сервис, два вызова `get`/`set`, замена Redis не планируется — **приемлемо**. Обёртка добавит файл и слой без выгоды.
- Пять сервисов знают формат ключей, TTL и pipeline-команды Redis — **дорого**. Замена или смена схемы ключей потребует править пять мест. Кандидат в P1/P2.

Вердикт для каждой стрелки: «дорого» или «приемлемо в этом контексте», с одной фразой почему. Учитывай:

- сколько consumers у зависимости;
- насколько детально они знают цель (только вызов метода или ещё формат данных, ошибки, конфигурацию);
- есть ли реальная причина ждать замену (несколько окружений, миграция в планах, тестовая подмена);
- сколько стоит обёртка (файл, интерфейс, DI-регистрация, ещё один уровень косвенности).

## Step 6 — Recommendations

Для каждого finding предложи **минимальное** изменение, которое снимает названную стоимость. Порядок предпочтений от дешёвого к дорогому:

1. Переместить код в правильный компонент, ничего не добавляя.
2. Передать данные параметром вместо импорта зависимости.
3. Выделить функцию или модуль без интерфейса.
4. Ввести interface / port с одной реализацией — только если нужна тестовая подмена или замена реально ожидается.
5. Ввести adapter, repository, service boundary, dependency inversion — когда consumers несколько и деталь цели протекает в них.

К каждой рекомендации обязательно три пункта:

1. **Какую проблему решает** — со ссылкой на evidence finding.
2. **Какую стоимость добавляет** — новые файлы, косвенность, DI, что читателю придётся держать в голове.
3. **Почему оправдана именно здесь** — число consumers, вероятность изменения, граница.

Если после этих трёх пунктов стоимость перевешивает — напиши прямо: «abstraction не нужна, оставить как есть», и объясни, при каком изменении контекста вердикт поменяется.
