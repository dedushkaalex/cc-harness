# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага.

## Step 0 — Code under review и контекст

Два вопроса до начала анализа: *что* проверяется и *что известно о планах*.

**Code under review.** Слово «scope» дальше означает только набор проверяемых concerns; для кода используй термин «код под ревью». Правило по умолчанию:

- если есть diff, PR или названы файлы — код под ревью это изменённые файлы плюс компоненты, которые они вызывают или которые вызывают их напрямую (один шаг по графу вызовов). Дальше не ходи;
- если попросили проверить модуль или сервис — все его файлы плюс один шаг наружу;
- весь репозиторий — только если так сказано явно. Тогда таблица Step 1 строится по модулям, а не по классам, и лимит из REPORT.md действует на модули.

Граница кода под ревью записывается в блок Scope отчёта.

**Контекст.** Вердикты «второй transport не планируется», «замена хранилища не ожидается», «правило нужно только здесь» нельзя брать из головы. Источники, в порядке надёжности:

1. ADR, `docs/`, design-документы — прямые утверждения о планах и принятых решениях;
2. README и CLAUDE.md — заявленный стек, окружения, ограничения;
3. git log за последние месяцы — что реально менялось и в какую сторону;
4. тесты — что подменяется, какие сценарии считаются важными;
5. конфиги окружений, `.env.example`, docker-compose — сколько окружений, какие технологии реально стоят рядом;
6. манифест зависимостей (`package.json`, `pyproject.toml`, `go.mod`, `mix.exs`, `Cargo.toml`, `pom.xml`) — какие библиотеки уже подключены, но не используются (признак начатой миграции).

Итог — короткий список «известно / не известно»:

```text
Известно:  один transport (HTTP), источник — README, docker-compose
Известно:  очередь для импорта в планах — ADR-0007
Не известно: планируется ли второе хранилище — в источниках нет
Базовая единица: trait + generic-параметр у consumer — источник: так объявлены все зависимости в `crates/*/src`; тесты подменяют через fake-реализации trait в `tests/`
```

То, чего в источниках нет, в finding записывается как допущение с пометкой в Confidence. Не ищи ответы дольше, чем занимает сам анализ: если за один проход по источникам ответа нет, это «не известно».

**Базовая единица.** Обязательная строка итога: механизм, которым в этом проекте объявляют зависимость — параметр конструктора, поле структуры, trait bound, `Protocol`, behaviour, `Context.Tag`, `Depends`, импорт модуля. Определяется по коду под ревью и соседним модулям, а не по тому, что обычно принято в стеке. Тесты (источник 4) подтверждают выбор, если подменяют зависимости через тот же механизм; если тесты ничего не подменяют, единица всё равно берётся по объявлениям, и это записывается рядом: «подмена в тестах: не используется». Эта строка не бывает «не известно». Если механизмов два, записываются оба и граница между ними. `backend-dependency-review` по этой строке отличает штатный способ объявить зависимость от лишней abstraction.

## Step 1 — Reconstruct

Цель — описать структуру такой, какая она есть в коде. Название папки `domain/` или `usecases/` ещё ничего не доказывает: смотри, что делает файл и с чем работает напрямую. README здесь не источник: он описывает желаемое, а таблица должна описывать существующее.

Определи для каждого компонента (класс, модуль, функция верхнего уровня, объявленный сервис; в Effect — `Context.Tag` с его Layer):

- **Слой** по тому, с чем компонент работает напрямую. Ровно шесть значений, те же, что у `backend-dependency-review`:
  - transport — HTTP/gRPC/queue handlers, request/response DTO, middleware, routing;
  - application — сценарии использования, оркестрация, транзакционные границы;
  - domain — правила предметной области, инварианты, вычисления без I/O;
  - infrastructure — кэш, очереди, файловая система, framework-специфика, конфигурация;
  - persistence — БД, ORM, repository, миграции;
  - external service — SDK и клиенты сторонних API.
- **Ответственность** одной фразой: «принимает HTTP-запрос на создание заказа и вызывает сценарий».
- **Использует**: всё, через что компонент получает другие компоненты: импорты (в том числе только типов), параметры конструкторов и функций, объявленные требования (в Effect — канал `R` и входы `Layer<Out, E, In>`; в FastAPI — `Depends`; в Rust — trait bound), глобальные объекты и конфигурация, аннотации и базовые типы. Это факт для карты, а не предмет оценки — стрелки оценивает `backend-dependency-review`.

Итог шага — таблица:

| Компонент | Слой | Ответственность | Использует |
|---|---|---|---|
| `OrderController` | transport | принимает запросы на заказы | `OrderService`, `PrismaClient` |
| `OrderService` | application | сценарий создания заказа | `OrderRepository`, `Clock` |

Строка `OrderController` использует `PrismaClient` — это подсказка для Step 3: посмотреть, не лежит ли в controller код persistence. Сама стрелка в finding не превращается.

## Step 2 — Responsibilities

Ищи **смешение видов работы**, а не объём. Класс с двадцатью методами одного вида (двадцать запросов к БД в repository) — норма. Класс с тремя методами трёх видов — кандидат в findings.

Признаки смешения по типам компонентов:

- **Controller / handler** парсит запрос *и* принимает бизнес-решение (проверяет баланс, считает скидку) *и* сам ходит в БД.
- **Application service / use case** оркестрирует сценарий *и* формирует HTTP-ответ или знает про status codes.
- **Domain object** содержит инварианты *и* сериализацию в формат БД или вызовы внешних API.
- **Repository** читает и пишет данные *и* принимает бизнес-решения («если заказ просрочен — отменить»).
- **External API client** делает вызов *и* решает, что делать с бизнес-результатом.
- **Infrastructure service** (mailer, cache, queue) содержит правила предметной области.

Для каждого компонента ответь: если завтра поменяется только транспорт / только хранилище / только бизнес-правило, придётся ли править этот файл? Файл, который правится по трём разным причинам, смешивает три ответственности.

Каждое найденное место — файл и строка. Эти места на Step 3 не повторяются.

## Step 3 — Boundaries

Граница держится, когда в компоненте лежит код только его слоя. Вопрос к каждому компоненту: **работу какого слоя выполняет этот код?** Если ответ не совпадает со слоем компонента из таблицы Step 1 — это место в findings.

Отличие от Step 2: там ищется компонент, который делает *несколько* видов работы, здесь — код, который делает *один* вид работы, но лежит в компоненте другого слоя. Одна и та же строка часто подходит под оба описания. Правило: **место, уже записанное на Step 2, на Step 3 не повторяется**. На Step 3 попадает только то, что Step 2 не поймал: компонент целиком делает одну работу, но не ту, которую подсказывает его слой (repository, который целиком состоит из бизнес-правил и одного запроса), или код чужого слоя в компоненте, который в остальном чистый.

Типовые случаи:

1. **Persistence в transport.** Handler строит запросы, открывает транзакцию, пишет в таблицы.
2. **Бизнес-правила в persistence или infrastructure.** Repository, cache-сервис или API client решают, что делать с результатом по правилам предметной области.
3. **Transport в application.** Сценарий формирует status code, заголовки, форму HTTP-ответа.
4. **I/O в domain.** Domain-объект сам ходит в БД или во внешний API.
5. **Всё в одном файле.** Handler читает тело запроса, проверяет правила и пишет в БД одной функцией.

Что сюда **не** входит: чужой тип в сигнатуре, чужой import, чужая ошибка, пробрасываемая наверх. Код при этом лежит на месте, протекло только знание — это leakage, его оценивает `backend-dependency-review`. Проверка: если исправление — перенести строки кода в другой файл, это здесь; если исправление — сменить тип или убрать import, это там.

Для каждого места зафиксируй файл, строку и слой, которому код принадлежит. Отдельно отметь границы, которые **уже держатся**: они пойдут в раздел «Good decisions».

## Step 4 — Recommendations

Для каждого finding предложи **минимальное перемещение кода**, которое снимает названную стоимость. Порядок предпочтений от дешёвого к дорогому:

1. Переместить код в существующий компонент правильного слоя.
2. Выделить функцию или модуль в правильном слое, если подходящего компонента нет.
3. Разбить компонент на два по видам работы.

Новых interface, port, adapter и слоёв-прослоек этот skill не предлагает. Если перемещение кода создаёт стрелку, которую хочется обернуть в abstraction («после переноса `OrderService` будет знать Prisma напрямую»), зафиксируй стрелку в «Вне scope» для `backend-dependency-review` и не оценивай её.

К каждой рекомендации обязательно три пункта:

1. **Какую проблему решает** — со ссылкой на evidence finding.
2. **Куда переносится код** — компонент и слой.
3. **Что становится хуже** — новый файл, длиннее вызов, компонент растёт.

Если перемещение дороже проблемы — напиши прямо: «оставить как есть», назови источник из Step 0, на котором это держится, и объясни, при каком изменении контекста вердикт поменяется.
