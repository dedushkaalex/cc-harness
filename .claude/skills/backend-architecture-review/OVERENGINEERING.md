# Оценка лишних abstraction

Справочник к overengineering pass из [SKILL.md](SKILL.md). Лишняя abstraction — это структура, за которую платят сейчас (косвенность, файлы, DI), а выгоду получат только при изменении, которого не будет.

## Что проверять

Каждый interface, abstract class, generic-обёртку, «слой-прослойку» (сервис, который только делегирует дальше), фабрику с одной веткой и базовый класс с одним наследником.

## Шесть критериев

Ответь на все шесть, прежде чем выносить вердикт. Ни один критерий сам по себе не решает.

| Критерий | Abstraction оправдана, когда | Abstraction лишняя, когда |
|---|---|---|
| **Число реализаций** | две и больше живых реализации в проде | одна, и второй не видно в планах |
| **Число consumers** | несколько модулей вызывают через контракт | один consumer, и он рядом с реализацией |
| **Вероятность изменения** | замена реально ожидается: миграция, несколько окружений, vendor lock известен как риск | «вдруг когда-нибудь поменяем» |
| **Тестовая подмена** | реализация делает I/O, которое в тестах нужно заменять, и подмена без интерфейса невозможна или уродлива | реализация чистая, либо подменить можно проще (фикстура, in-memory клиент, mock модуля) |
| **Architectural boundary** | контракт стоит на границе слоёв и удерживает её | контракт внутри одного слоя между двумя соседними файлами |
| **Стоимость сложности** | добавленная косвенность — один файл и одна регистрация | новый файл, интерфейс, DI-токен, фабрика, и читателю нужно пройти три перехода, чтобы найти реальный код |

## Пример: `PasswordHasher`

```ts
interface PasswordHasher {
  hash(plain: string): Promise<string>;
  verify(plain: string, hashed: string): Promise<boolean>;
}

class Argon2PasswordHasher implements PasswordHasher { ... }
```

Одна и та же пара «interface + реализация» получает разные вердикты в зависимости от ответов на критерии.

**Лишняя**, если: одна реализация, единственный consumer — `RegisterUserService`, смена алгоритма не планируется, а в тестах хэширование и так работает быстро на тестовых параметрах. Стоимость — интерфейс, DI-регистрация и лишний переход при чтении. Рекомендация: использовать класс напрямую; интерфейс появится в момент, когда придёт вторая реализация.

**Оправдана**, если: хэшер используют регистрация, смена пароля и импорт пользователей из legacy-системы с другим алгоритмом (уже две реализации), а в интеграционных тестах argon2 с боевыми параметрами делает каждый тест на секунду дольше. Здесь контракт стоит на границе application → infrastructure и экономит время всем трём consumers.

## Как записывать в отчёт

В раздел «Overengineering» попадают только abstraction с вердиктом «лишняя». Для каждой:

- что за структура и где (файл:строка);
- какие из шести критериев не выполнены;
- что она стоит сейчас;
- минимальное упрощение и при каком изменении контекста abstraction стоит вернуть.

Abstraction с вердиктом «оправдана» идёт в «Good decisions» с одной фразой, какой критерий её оправдывает.
