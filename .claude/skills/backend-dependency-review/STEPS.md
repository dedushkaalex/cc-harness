# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага. Step 5 и overengineering pass описаны отдельно в [INVERSION.md](INVERSION.md).

## Step 1 — Reconstruct dependency graph

Цель — увидеть связи такими, какие они есть в коде. Название папки `domain/` или `ports/` ничего не доказывает: стрелка существует там, где один файл получает другой.

**Если есть отчёт `backend-architecture-review`** — он идёт первым в pipeline, и его Architecture summary с таблицей компонентов — начальная модель. Возьми оттуда имена компонентов, слои и колонку «использует», чтобы оба отчёта говорили об одних и тех же вещах одними словами. Дальше — проверка по коду, потому что предыдущий агент мог что-то пропустить: у каждой строки «использует» найди файл и строку, где стрелка видна. Дополняй модель только тем, что нужно для dependency analysis — импорты типов, DI-регистрации модулей, декораторы, наследование; не перестраивай карту целиком. Слой компонента из отчёта не переопределяй; если он явно не совпадает с кодом, отметь это одной строкой в «Вне scope» для architecture-review.

**Стрелки после переноса кода.** Оба skill смотрят на один и тот же код. Если первый отчёт предлагает перенести транзакцию из `OrderController` в `OrderService`, стрелка `OrderController → Prisma` исчезнет вместе с переносом — её не оценивай, иначе получится второй finding про ту же строку. Оценивай стрелку, которая появится после переноса: `OrderService → Prisma`. В Dependency map так и пиши: «после переноса из finding [P2] architecture-review».

**Если отчёта нет** — строй карту с нуля по правилам ниже.

Где искать стрелки:

- **Импорты** — самый очевидный источник. Импорт типа тоже считается: `import type { Prisma } from '@prisma/client'` в application service — это стрелка `Application → Prisma`.
- **Конструкторы и DI** — что инжектится, под каким токеном, конкретный класс или interface.
- **DI-регистрации модулей** — `providers`, `imports`, `exports` в NestJS-модулях показывают зависимости между модулями, которых нет в импортах файлов.
- **Глобальные объекты и singletons** — `process.env`, глобальный клиент БД, статические методы.
- **Декораторы framework** — `@Entity`, `@Injectable`, `@Controller` на классе делают класс зависимым от framework или ORM.
- **Наследование** — базовый класс из ORM или framework.

Для каждой стрелки запиши:

```text
OrderService (application) → PrismaClient (persistence)   src/orders/order.service.ts:12
OrderService (application) → Redis (infrastructure)        src/orders/order.service.ts:14
OrderController (transport) → OrderService (application)   src/orders/order.controller.ts:8
```

Слой определяй по тому, с чем компонент работает напрямую: transport — HTTP/gRPC/queue handlers и DTO; application — сценарии и оркестрация; domain — правила без I/O; infrastructure — кэш, очереди, файлы, framework; persistence — БД, ORM, repository; external services — SDK и клиенты сторонних API.

Особое внимание — стрелкам между разными слоями. Стрелки внутри слоя (два application service вызывают друг друга) важны только на Step 6.

## Step 2 — Direction

Подозрительная стрелка — любая из:

```text
Domain → Framework
Domain → ORM
Domain → Database
Domain → Redis
Domain → Transport DTO
Application → concrete infrastructure (клиент, SDK, драйвер, а не контракт)
Transport → Persistence в обход application
Модуль → implementation detail другого модуля (его таблица, формат кэша, приватный тип)
```

Для каждой ответь письменно:

1. **Consumer** — какой именно компонент зависит. Не слой, а класс или модуль.
2. **Dependency** — от чего именно. `Redis` — слишком грубо; `ioredis` `Redis` клиент с командами `hset` и `expire` — точно.
3. **Почему стрелка существует** — что consumer получает: данные, побочный эффект, тип, поведение.
4. **Business concept или implementation detail** — зависит ли consumer от *того, что* делает цель («сохранить сессию») или от *того, как* она это делает (ключ `session:{id}`, TTL в секундах, pipeline).

Стрелка `Domain → ORM` не становится finding автоматически. Если domain-объект — это TypeORM entity, у проекта нет отдельного domain слоя и никто не планирует его вводить, это архитектурное решение проекта, а не протечка. Finding появится, когда назовёшь изменение, которое из-за этого стало дорогим.

## Step 3 — Leakage

Протечка — деталь одного компонента, видимая за его границей. Типовые случаи:

| Что протекло | Через какую границу | Как выглядит в коде |
|---|---|---|
| Типы ORM (Prisma, TypeORM entity, QueryBuilder) | persistence → application или transport | application service возвращает `Prisma.UserGetPayload`; controller отдаёт entity как response |
| Redis-специфичные типы и concepts | infrastructure → application | сервис оперирует ключами, TTL, `pipeline`, `Buffer` из ioredis |
| HTTP DTO | transport → application или domain | `CreateOrderDto` с `@ApiProperty` принимается domain-функцией |
| Декораторы и типы framework | framework → domain | domain-класс помечен `@Injectable`, импортирует `Request` из express |
| Database entity как domain entity | persistence → domain | правила предметной области живут в классе с `@Entity`, `@Column` |
| Ошибки инфраструктуры | infrastructure → application или transport | `QueryFailedError`, `RedisError`, `AxiosError` доходят до controller без преобразования |
| Формат внешнего API | external service → application | сценарий разбирает JSON стороннего API по его полям |

Для каждой протечки зафиксируй три вещи:

1. **Что именно протекло** — конкретный тип, ошибка, формат.
2. **Через какую границу** — из какого слоя в какой.
3. **Какие изменения теперь дороже** — смена ORM правит controller; новая версия внешнего API правит сценарий; замена Redis ломает сигнатуры application service.

Плюс файл и строка. Отдельно отметь границы, которые **уже держатся** — repository возвращает свои типы, а не entity; ошибки инфраструктуры оборачиваются на границе. Они пойдут в раздел «Good dependencies».

Ошибки как канал протечки — не тема error handling. Здесь вопрос только один: знает ли верхний слой о типе ошибки нижнего. Корректность самой обработки проверяет другой skill.

## Step 4 — Coupling

Для каждой существенной стрелки (подозрительной из Step 2 или несущей протечку из Step 3) оцени шесть параметров:

| Параметр | Дёшево | Дорого |
|---|---|---|
| **Знание о concrete implementation** | consumer вызывает метод контракта | consumer знает SDK, формат ключей, схему таблицы, коды ошибок |
| **Число consumers** | один компонент рядом с целью | несколько модулей в разных частях системы |
| **Стоимость замены** | замена — правка одного файла | правки разбросаны, и найти их можно только поиском по импортам |
| **Распространение типов и concepts** | типы цели не выходят за пределы одного компонента | типы цели в сигнатурах, DTO, ответах API |
| **Stable или volatile** | standard library, устоявшийся внутренний контракт | конкретная инфраструктурная технология, внешний API, SDK с частыми breaking changes |
| **Contract или implementation detail** | стрелка ведёт к business/application contract | стрелка ведёт к тому, как контракт реализован |

Вердикт для каждой стрелки: **«дорого»** или **«приемлемо в этом контексте»**, с одной фразой почему.

Пример: `SessionService → ioredis`.

- Один сервис, вызовы `get` и `set`, Redis-типы наружу не выходят, замена не планируется — **приемлемо**. Обёртка добавит файл и переход без выгоды.
- Четыре сервиса знают формат ключей `session:{userId}:{jti}`, TTL и `pipeline` — **дорого**. Смена схемы ключей или переход на другое хранилище потребует править четыре места. Кандидат в P1/P2, дальше — Step 5.

Некоторое coupling естественно и полезно: application service, который знает свой repository, controller, который знает свой сервис. Не ищи проблему там, где нет change scenario.

## Step 6 — Cycles

Цикл — путь по стрелкам, который возвращается в исходную точку:

```text
A → B → C → A
Users → Sessions → Users
```

Ищи на трёх уровнях: файлы (circular import), компоненты (два сервиса инжектят друг друга, `forwardRef`), модули (два NestJS-модуля импортируют друг друга).

Технический circular import сам по себе — не finding. Оцени, к чему цикл приводит:

1. **Независимое изменение невозможно** — правка одного участника требует правки другого.
2. **Сложная инициализация** — `forwardRef`, lazy-инъекция, порядок регистрации, о котором надо помнить.
3. **Circular imports** — `undefined` на этапе загрузки модуля, обходы через отложенный импорт.
4. **Изолированное тестирование невозможно** — чтобы протестировать A, нужно поднять B и C.
5. **Размытое ownership** — непонятно, какой модуль владеет концепцией, потому что оба её меняют.

Цикл с одним–двумя признаками из пяти — обычно P2 или P3; цикл, который блокирует тестирование и требует `forwardRef` — кандидат в P1. Решение обычно одно из: вынести общую часть в третий компонент, передать данные параметром вместо вызова назад, перевернуть одну стрелку через событие или callback.

## Step 7 — Stable vs volatile

Проверочный проход по всем findings. Вопрос:

> Какая сторона стрелки скорее будет изменяться?

Dependency оправдывает внимание, когда **цель** изменчивее consumer. `Application → Redis`: Redis — конкретная технология, может смениться, стрелка несёт change cost. `Application → standard library`, `Application → собственный устоявшийся value object` — цель стабильнее consumer, стрелка естественна.

Для каждого finding подтверди, что изменчивая сторона — именно dependency. Если цель стабильна, а finding держится только на «это нарушает направление слоёв», понизь его до P3 или убери и напиши почему. Не применяй dependency inversion механически: переворачивать стрелку к стабильной цели — это добавлять complexity без выгоды.
