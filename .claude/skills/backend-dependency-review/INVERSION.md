# Abstraction в обе стороны

Справочник к Step 5 и overengineering pass из [SKILL.md](SKILL.md). Один и тот же вопрос — «нужна ли здесь граница?» — задаётся дважды: перед тем как предложить контракт, и перед тем как оставить существующий.

## Что считается базовой единицей, а что — abstraction

**Базовая единица стека** — тот механизм, которым в проекте объявляют зависимость. Подмена в тестах через тот же механизм подтверждает выбор; её отсутствие единицу не отменяет: contract с одной реализацией и без тестовой подмены остаётся базовой единицей, если так объявлены зависимости в проекте. Она не abstraction, а штатный способ сказать «мне нужно вот это». Overengineering pass её не трогает. Лишним считается то, что стоит **поверх** базовой единицы и не добавляет поведения. Без ответа «что здесь базовая единица» pass даёт ложные срабатывания, поэтому ответ записывается на Step 0 в блок Scope строкой «базовая единица: механизм, источник» — по коду и тестам, а не по знакомому стеку.

Два правила, которые следуют из этого определения:

- **Contract с одной реализацией** — abstraction только там, где стек умеет подменять зависимость и без него. Если contract и есть единственный способ объявить и подменить зависимость, он базовая единица.
- **Критерий «нужна для тестов»** весит тем меньше, чем проще в стеке подмена без contract: override provider, мок модуля, monkeypatch, `dependency_overrides`.

Примеры калибровки:

- **Effect.** Базовая единица — `Context.Tag` + Live Layer + Test Layer. Тестовый Layer рядом с живым — норма. Лишнее: Tag, который только оборачивает другой Tag; Layer, собранный из одного Layer без добавления; interface или abstract class, дублирующие форму сервиса, уже описанную в Tag; фабрика над Layer; сервисный класс между Tag и реализацией.
- **Go.** Базовая единица — маленький interface на стороне consumer и структура-реализация; с одной реализацией это идиома, не abstraction. Лишнее: interface на стороне реализации, повторяющий её целиком; interface поверх interface; фабрика с одной веткой.
- **Python с DI (FastAPI `Depends`, контейнер).** Базовая единица — функция или класс, подменяемые через `dependency_overrides` или контейнер. `Protocol` с одной реализацией — abstraction, оправдана только если подмена через контейнер не работает.
- **DI-контейнер (NestJS, Spring, .NET) и plain-модули.** Базовая единица — класс или модуль с функциями. Interface с одной реализацией — abstraction, проходит через критерии ниже. Подмена в тестах возможна через override provider или мок модуля, поэтому «нужна для тестов» здесь слабый аргумент.
- **Elixir.** Базовая единица — модуль; behaviour с одной реализацией и подменой через config или `Mox` — базовая единица, если тесты через неё идут; иначе abstraction.

Если в проекте несколько стилей одновременно, каждая abstraction оценивается по правилам своего стиля.

## Step 5 — Dependency inversion

Кандидаты — стрелки с вердиктом «дорого» из Step 4. Пример превращения:

```text
SessionService
      ↓
Redis
```

в:

```text
SessionService
      ↓
SessionStore          (contract в терминах приложения: save, find, revoke)
      ↑
RedisSessionStore     (adapter — единственное место, знающее ключи, TTL, pipeline)
      ↓
Redis
```

Контракт не предлагается автоматически. Перед рекомендацией ответь на пять вопросов письменно:

| Вопрос | Ответ, который оправдывает abstraction | Ответ, который её отменяет |
|---|---|---|
| **Какую конкретную dependency problem решает** | «четыре сервиса знают формат ключей Redis» | «так правильнее по слоям» |
| **Какие изменения локализует** | смена схемы ключей, замена хранилища, тестовая подмена — всё в одном файле | изменений, которые стали бы дешевле, назвать не удаётся |
| **Сколько complexity добавляет** | один contract, одна реализация, одна регистрация в сборке | Tag + interface + abstract class + фабрика; читателю три перехода до реального кода |
| **Есть ли уже похожая abstraction в проекте** | нет, или есть и её можно переиспользовать | есть, и новая дублирует её под другим именем |
| **Действительно ли эта boundary нужна** | consumers несколько, цель volatile (источник — Context), деталь цели протекает | один consumer, цель стабильна, замена не ожидается |

Если хотя бы два ответа попадают в правую колонку — abstraction, скорее всего, не нужна. Порядок предпочтений от дешёвого к дорогому:

1. **Переместить стрелку** — перенести вызов инфраструктуры из consumer в компонент, который уже ей владеет.
2. **Передать данные параметром** — consumer получает результат, а не клиента.
3. **Выделить модуль или функцию без контракта** — один файл, который знает Redis.
4. **Contract с одной реализацией** — стоит столько, сколько стек берёт за него: ничего, если contract и есть базовая единица (Effect Tag, Go interface у consumer), тогда это шаг 3 и 4 одновременно; файл и переход, если подмена возможна и без него, тогда только если нужна тестовая подмена или замена реально ожидается.
5. **Adapter, dependency inversion, extraction of a boundary** — когда consumers несколько и деталь цели протекает в них.

К каждой рекомендации в отчёте — три пункта: какую проблему решает (ссылка на evidence), какую стоимость добавляет, почему оправдана именно здесь. Если стоимость перевешивает — «abstraction не нужна, оставить как есть» и при каком изменении контекста вердикт поменяется.

## Overengineering pass

Обратная проблема: структура, за которую платят сейчас — косвенность, файлы, токены — а выгоду получат только при изменении, которого не будет. Excessive indirection хуже прямой зависимости: читатель проходит пять переходов, чтобы найти вызов `argon2.hash`.

Проверяй всё, что стоит поверх базовой единицы стека: contract поверх contract, adapter поверх adapter, abstract class рядом с contract, generic-обёртку, слой-прослойку (сервис, который только делегирует дальше), фабрику с одной веткой, базовый класс с одним наследником. В Effect это Tag поверх Tag, Layer поверх Layer, классы и interface рядом с Tag; в стеке с DI-контейнером — interface поверх класса, который и так подменяется контейнером.

Пример цепочки:

```text
Application
    ↓
IPasswordHasher
    ↓
PasswordHasherService
    ↓
PasswordHasherFactory
    ↓
Argon2PasswordHasher
    ↓
Argon2
```

Лишняя, если одновременно:

- **одна реализация** — и второй не видно в планах (источник — Context, иначе Confidence не выше medium);
- **один consumer** — и он рядом с реализацией;
- **нет meaningful change boundary** — смена алгоритма не планируется, окружение одно;
- **abstraction не используется для isolation** — в тестах реализация всё равно вызывается напрямую или подменяется в обход контракта.

Стоимость сейчас: четыре файла, три перехода, токен и фабрика, чтобы вызвать одну функцию. Упрощение: `Argon2PasswordHasher` используется напрямую; контракт вернуть в момент, когда появится вторая реализация или тестовая подмена через него.

Та же цепочка в Effect выглядит как `PasswordHasher` Tag + `PasswordHasherLive` Layer поверх argon2 + `PasswordHasherTest` Layer. Это базовая единица, не finding. Лишними будут `PasswordHasherService` и `PasswordHasherFactory` между Tag и Layer: Tag с одним прямым Layer решает ту же задачу.

Та же цепочка в Go: `type PasswordHasher interface` рядом с consumer и `argon2Hasher` — базовая единица, если тесты подменяют через него; `PasswordHasherService` и фабрика между ними — лишние.

Та же цепочка **оправдана** в стеке с DI-контейнером, если хэшер используют регистрация, смена пароля и импорт из legacy-системы с другим алгоритмом (две реализации), а в интеграционных тестах argon2 с боевыми параметрами замедляет каждый тест. Контракт стоит на границе application → infrastructure и экономит всем трём consumers. Но и тогда прослойки между interface и реализацией — лишние.

## Как записывать в отчёт

В раздел «Overengineering» — только abstraction с вердиктом «лишняя»: что за структура и где (файл:строка), какие критерии не выполнены, что стоит сейчас, минимальное упрощение, при каком изменении контекста вернуть.

Abstraction с вердиктом «оправдана» — в «Good dependencies» с одной фразой, какой критерий её оправдывает.
