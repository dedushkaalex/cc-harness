# Abstraction в обе стороны

Справочник к Step 5 и overengineering pass из [SKILL.md](SKILL.md). Один и тот же вопрос — «нужна ли здесь граница?» — задаётся дважды: перед тем как предложить контракт, и перед тем как оставить существующий.

## Базовая единица и критерии оценки

**Базовая единица** — минимальная форма, в которой в этом коде объявляют зависимость: параметр конструктора или функции, поле структуры, trait bound, `Protocol`, behaviour, `Context.Tag`, `Depends`, импорт модуля. Определяется на Step 0 по коду под ревью и тестам, а не по знакомому стеку, и записывается в блок Scope строкой «базовая единица: механизм, источник». Её единственная роль — задать **нулевую точку стоимости indirection**: граница, совпадающая с этой формой, не добавляет файлов и переходов; граница поверх неё стоит столько, сколько добавляет. Больше базовая единица ничего не решает.

Любая граница — contract, adapter, обёртка, фабрика, прослойка — оценивается одними и теми же критериями:

- число consumers;
- число реализаций;
- ожидаемое изменение — с источником из Context;
- volatility цели;
- нужна ли подмена — в тестах или между окружениями;
- объём indirection сверх нулевой точки;
- дублируется ли знание о технологии между компонентами;
- есть ли содержательная граница между «что» и «как».

Механизм стека меняет evidence и стоимость, но не критерии и не вердикт. Effect Tag, Go interface, Python `Depends`, NestJS provider, Elixir behaviour — разные способы выразить одну и ту же зависимость, а не разные архитектурные правила. Contract с одной реализацией, одним consumer и без подмены получает один и тот же вердикт в любом стеке; различается только стоимость: ноль, если contract совпадает с базовой единицей, файл и переход, если стоит поверх неё. Вердикт «лишняя» для границы с нулевой стоимостью возможен только с названным упрощением — например, прямой импорт функции вместо объявленного сервиса, когда у сервиса нет собственных объявленных зависимостей.

Критерий «нужна для тестов» весит тем меньше, чем проще в этом коде подмена без contract: override provider, мок модуля, monkeypatch, `dependency_overrides`.

Примеры калибровки — только иллюстрации того, как выглядит нулевая точка. Они не решают, лишняя ли структура:

- **Effect.** Нулевая точка — `Context.Tag` + Layer. Tag с одним Layer и тестовым Layer рядом стоит ноль. Tag поверх Tag, Layer из одного Layer без добавления, interface или abstract class, дублирующие форму Tag, фабрика над Layer, сервисный класс между Tag и реализацией — стоят переход каждый и проходят критерии.
- **Go.** Нулевая точка — параметр функции или поле структуры. Interface на стороне consumer стоит ноль, если так объявлены зависимости в коде под ревью, и один переход, если в остальном коде структуры передаются напрямую. Interface на стороне реализации, повторяющий её целиком, interface поверх interface, фабрика с одной веткой — проходят критерии.
- **Python с DI (FastAPI `Depends`, контейнер).** Нулевая точка — функция или класс, подменяемые через `dependency_overrides` или контейнер. `Protocol` поверх них стоит файл и переход.
- **DI-контейнер (NestJS, Spring, .NET) и plain-модули.** Нулевая точка зависит от того, как объявлены зависимости в коде: если классом с подменой через override provider — interface стоит переход; если interface в параметре конструктора с подменой через регистрацию — interface и есть нулевая точка, а переход стоит то, что поверх него.
- **Elixir.** Нулевая точка — модуль. Behaviour с подменой через config или `Mox` стоит ноль, если так объявлены зависимости, и переход, если подмена идёт в обход.

Если в проекте два механизма, граница между ними записана на Step 0, и стоимость каждой границы считается относительно механизма своего участка.

## Step 5 — Dependency inversion

Кандидаты — стрелки с вердиктом «дорого» из Step 4. Пример превращения:

```text
SessionService
      ↓
Redis
```

в:

```text
SessionService
      ↓
SessionStore          (contract в терминах приложения: save, find, revoke)
      ↑
RedisSessionStore     (adapter — единственное место, знающее ключи, TTL, pipeline)
      ↓
Redis
```

Контракт не предлагается автоматически. Перед рекомендацией ответь на пять вопросов письменно:

| Вопрос | Ответ, который оправдывает abstraction | Ответ, который её отменяет |
|---|---|---|
| **Какую конкретную dependency problem решает** | «четыре сервиса знают формат ключей Redis» | «так правильнее по слоям» |
| **Какие изменения локализует** | смена схемы ключей, замена хранилища, тестовая подмена — всё в одном файле | изменений, которые стали бы дешевле, назвать не удаётся |
| **Сколько complexity добавляет** | один contract, одна реализация, одна регистрация в сборке | Tag + interface + abstract class + фабрика; читателю три перехода до реального кода |
| **Есть ли уже похожая abstraction в проекте** | нет, или есть и её можно переиспользовать | есть, и новая дублирует её под другим именем |
| **Действительно ли эта boundary нужна** | consumers несколько, цель volatile (источник — Context), деталь цели протекает | один consumer, цель стабильна, замена не ожидается |

Если хотя бы два ответа попадают в правую колонку — abstraction, скорее всего, не нужна. Порядок предпочтений от дешёвого к дорогому:

1. **Переместить стрелку** — перенести вызов инфраструктуры из consumer в компонент, который уже ей владеет.
2. **Передать данные параметром** — consumer получает результат, а не клиента.
3. **Выделить модуль или функцию без контракта** — один файл, который знает Redis.
4. **Contract с одной реализацией** — стоит столько, сколько добавляет сверх нулевой точки: ничего, если contract совпадает с базовой единицей из Step 0, тогда это шаг 3 и 4 одновременно; файл и переход, если стоит поверх неё, тогда только если нужна подмена или замена реально ожидается (источник — Context).
5. **Adapter, dependency inversion, extraction of a boundary** — когда consumers несколько и деталь цели протекает в них.

К каждой рекомендации в отчёте — три пункта: какую проблему решает (ссылка на evidence), какую стоимость добавляет, почему оправдана именно здесь. Если стоимость перевешивает — «abstraction не нужна, оставить как есть» и при каком изменении контекста вердикт поменяется.

## Overengineering pass

Обратная проблема: структура, за которую платят сейчас — косвенность, файлы, токены — а выгоду получат только при изменении, которого не будет. Excessive indirection хуже прямой зависимости: читатель проходит пять переходов, чтобы найти вызов `argon2.hash`.

Проверяй каждую границу по критериям из раздела выше, начиная с тех, что стоят поверх нулевой точки: contract поверх contract, adapter поверх adapter, abstract class рядом с contract, generic-обёртку, слой-прослойку (сервис, который только делегирует дальше), фабрику с одной веткой, базовый класс с одним наследником. Граница на нулевой точке проходит те же критерии со стоимостью ноль. Примеры: в Effect — Tag поверх Tag, Layer поверх Layer, классы и interface рядом с Tag; в стеке с DI-контейнером — interface поверх класса, который и так подменяется контейнером, или прослойка между interface и реализацией.

Пример цепочки:

```text
Application
    ↓
IPasswordHasher
    ↓
PasswordHasherService
    ↓
PasswordHasherFactory
    ↓
Argon2PasswordHasher
    ↓
Argon2
```

Лишняя, если одновременно:

- **одна реализация** — и второй не видно в планах (источник — Context, иначе Confidence не выше medium);
- **один consumer** — и он рядом с реализацией;
- **нет meaningful change boundary** — смена алгоритма не планируется, окружение одно;
- **abstraction не используется для isolation** — в тестах реализация всё равно вызывается напрямую или подменяется в обход контракта.

Стоимость сейчас: четыре файла, три перехода, токен и фабрика, чтобы вызвать одну функцию. Упрощение: `Argon2PasswordHasher` используется напрямую; контракт вернуть в момент, когда появится вторая реализация или тестовая подмена через него.

Та же цепочка в Effect выглядит как `PasswordHasher` Tag + `PasswordHasherLive` Layer поверх argon2 + `PasswordHasherTest` Layer. Стоимость ноль, подмена через Tag используется — оправдана. Без тестового Layer и с одним consumer Tag проходит те же критерии, что interface в NestJS: упрощение — прямой импорт функции хэширования, если у неё нет собственных объявленных зависимостей. `PasswordHasherService` и `PasswordHasherFactory` между Tag и Layer лишние в любом случае: Tag с одним прямым Layer решает ту же задачу.

Та же цепочка в Go: `type PasswordHasher interface` рядом с consumer и `argon2Hasher` — те же критерии: оправдан, если через него идёт подмена или есть вторая реализация; иначе один переход без выгоды, упрощение — передать `argon2Hasher` напрямую. `PasswordHasherService` и фабрика между ними лишние в любом случае.

Та же цепочка **оправдана** в стеке с DI-контейнером, если хэшер используют регистрация, смена пароля и импорт из legacy-системы с другим алгоритмом (две реализации), а в интеграционных тестах argon2 с боевыми параметрами замедляет каждый тест. Контракт стоит на границе application → infrastructure и экономит всем трём consumers. Но и тогда прослойки между interface и реализацией — лишние.

## Как записывать в отчёт

В раздел «Overengineering» — только abstraction с вердиктом «лишняя»: что за структура и где (файл:строка), какие критерии не выполнены, что стоит сейчас, минимальное упрощение, при каком изменении контекста вернуть.

Abstraction с вердиктом «оправдана» — в «Good dependencies» с одной фразой, какой критерий её оправдывает.
