# Abstraction в обе стороны

Справочник к Step 5 и overengineering pass из [SKILL.md](SKILL.md). Один и тот же вопрос — «нужна ли здесь граница?» — задаётся дважды: перед тем как предложить interface, и перед тем как оставить существующий.

## Step 5 — Dependency inversion

Кандидаты — стрелки с вердиктом «дорого» из Step 4. Пример превращения:

```text
SessionService
      ↓
Redis
```

в:

```text
SessionService
      ↓
SessionStore          (контракт в терминах приложения: save, find, revoke)
      ↑
RedisSessionStore     (единственное место, знающее ключи, TTL, pipeline)
      ↓
Redis
```

Interface или port не предлагается автоматически. Перед рекомендацией ответь на пять вопросов письменно:

| Вопрос | Ответ, который оправдывает abstraction | Ответ, который её отменяет |
|---|---|---|
| **Какую конкретную dependency problem решает** | «четыре сервиса знают формат ключей Redis» | «так правильнее по слоям» |
| **Какие изменения локализует** | смена схемы ключей, замена хранилища, тестовая подмена — всё в одном файле | изменений, которые стали бы дешевле, назвать не удаётся |
| **Сколько complexity добавляет** | один interface, одна реализация, одна DI-регистрация | interface + abstract class + фабрика + токен; читателю три перехода до реального кода |
| **Есть ли уже похожая abstraction в проекте** | нет, или есть и её можно переиспользовать | есть, и новая дублирует её под другим именем |
| **Действительно ли эта boundary нужна** | consumers несколько, цель volatile, деталь цели протекает | один consumer, цель стабильна, замена не ожидается |

Если хотя бы два ответа попадают в правую колонку — abstraction, скорее всего, не нужна. Порядок предпочтений от дешёвого к дорогому:

1. **Переместить стрелку** — перенести вызов инфраструктуры из consumer в компонент, который уже ей владеет.
2. **Передать данные параметром** — consumer получает результат, а не клиента.
3. **Выделить модуль или функцию без interface** — `sessionStore.ts` с обычными функциями, один файл, который знает Redis.
4. **Interface / port с одной реализацией** — только если нужна тестовая подмена или замена реально ожидается.
5. **Adapter, dependency inversion, extraction of a boundary** — когда consumers несколько и деталь цели протекает в них.

К каждой рекомендации в отчёте — три пункта: какую проблему решает (ссылка на evidence), какую стоимость добавляет, почему оправдана именно здесь. Если стоимость перевешивает — «abstraction не нужна, оставить как есть» и при каком изменении контекста вердикт поменяется.

## Overengineering pass

Обратная проблема: структура, за которую платят сейчас — косвенность, файлы, DI-токены — а выгоду получат только при изменении, которого не будет. Excessive indirection хуже прямой зависимости: читатель проходит пять переходов, чтобы найти вызов `argon2.hash`.

Проверяй каждый interface, port, adapter, abstract class, generic-обёртку, слой-прослойку (сервис, который только делегирует дальше), фабрику с одной веткой, базовый класс с одним наследником.

Пример цепочки:

```text
Application
    ↓
IPasswordHasher
    ↓
PasswordHasherService
    ↓
PasswordHasherFactory
    ↓
Argon2PasswordHasher
    ↓
Argon2
```

Лишняя, если одновременно:

- **одна реализация** — и второй не видно в планах;
- **один consumer** — и он рядом с реализацией;
- **нет meaningful change boundary** — смена алгоритма не планируется, окружение одно;
- **abstraction не используется для isolation** — в тестах реализация всё равно вызывается напрямую или подменяется мок-модулем, а не через interface.

Стоимость сейчас: четыре файла, три перехода, DI-токен и фабрика, чтобы вызвать одну функцию. Упрощение: `Argon2PasswordHasher` инжектится напрямую; interface вернуть в момент, когда появится вторая реализация или тестовая подмена через контракт.

Та же цепочка **оправдана**, если хэшер используют регистрация, смена пароля и импорт из legacy-системы с другим алгоритмом (две реализации), а в интеграционных тестах argon2 с боевыми параметрами замедляет каждый тест. Контракт стоит на границе application → infrastructure и экономит всем трём consumers. Но и тогда `PasswordHasherService` и `PasswordHasherFactory` между interface и реализацией — лишние слои: interface с одной прямой реализацией решает ту же задачу.

## Как записывать в отчёт

В раздел «Overengineering» — только abstraction с вердиктом «лишняя»: что за структура и где (файл:строка), какие критерии не выполнены, что стоит сейчас, минимальное упрощение, при каком изменении контекста вернуть.

Abstraction с вердиктом «оправдана» — в «Good dependencies» с одной фразой, какой критерий её оправдывает.
