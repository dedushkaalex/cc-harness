# Backend review — оркестратор pipeline

## Primary job

> После прогона каждая строка «Вне scope» и каждый Mismatch дошли до владельца и получили вердикт; ни одно место в коде не описано двумя findings; итоговый отчёт один.

Оркестратор не владеет ни одной категорией findings: ни один его критерий не создаёт finding, не меняет severity или confidence и не даёт вердикт «finding / non-finding» по коду. Все категории — в матрице `.claude/skills/README.md`, и этим skill она не меняется. Всё, что оркестратор сам замечает в коде, никуда не записывается.

## Делает / не делает

| Делает | Не делает (кто делает) |
|---|---|
| определяет код под ревью один раз: diff плюс один шаг по графу вызовов | не расширяет границу «раз уж смотрим» — граница из Stage A действует до конца прогона |
| собирает общий Context один раз — блок `Shared context` | не оценивает код: findings, non-findings, existing protections — пять скиллов |
| запускает скиллы по порядку и передаёт им Scope + Summary предыдущих | не передаёт полные findings — skill сам читает нужное место из отчёта на диске |
| проверяет, что каждая строка «Вне scope» и Mismatch получила вердикт владельца | не даёт вердикт вместо владельца — незакрытое идёт в `Unresolved handoffs` |
| снимает дубли по матрице владения из README | не решает содержательные конфликты — обе позиции идут в `Conflicts` |
| проверяет у каждого finding обязательные поля | не правит текст, severity, confidence — finding без поля идёт в `Dropped` |
| собирает единый отчёт по REPORT.md | не переписывает отчёты скиллов — только читает их |

Правило на границе: если действие меняет то, что читатель узнает о коде (finding появился, исчез, сменил уровень), — это не работа оркестратора. Если оно меняет только то, где и сколько раз читатель это прочтёт, — работа оркестратора.

## Стадии

Что именно передаётся, что проверяется и что делать при сбое — в [PROTOCOL.md](PROTOCOL.md). Стадия закрыта, когда выполнен её критерий.

- [ ] **Stage A — Shared context, один раз.** По аргументу (PR или diff; модуль; репозиторий — только явно) определи код под ревью по правилу соседей и собери общий Context одним проходом по источникам: «известно / не известно» с источниками, deployment model, источники повторов, базовая единица зависимости, базовая единица ошибки. Критерий: блок `Shared context` записан в `<output-dir>/shared-context.md` в формате, который каждый skill вставляет в свой Scope без переделки.
- [ ] **Stage B — Последовательный запуск.** `backend-architecture-review` → `backend-dependency-review` → `backend-domain-review` → `backend-persistence-review` → `backend-error-handling-review`, каждый отдельным агентом. Ему передаются `Shared context`, блоки Scope и Summary предыдущих отчётов и строки handoff, адресованные ему: раздел «Вне scope» и строки с его именем внутри findings, собранные `grep` по отчётам на диске. Skill пишет полный отчёт в `<output-dir>/<skill>.md`, в контексте оркестратора остаются только Scope и Summary. Сбой — один повтор, затем режим «без этого отчёта». Критерий: пять файлов отчётов или явные записи о пропуске.
- [ ] **Stage C — Замыкание handoff.** Для каждой строки «Вне scope» и каждого Mismatch проверь, что в отчёте владельца есть вердикт на то же место: finding, Non-finding или existing protection с тем же файлом и строкой. Без вердикта — один адресный проход владельца только по этим строкам. Критерий: у каждой строки статус closed / unresolved / not assigned.
- [ ] **Stage D — Дубли и конфликты.** Одно место в findings двух скиллов — владелец по матрице, чужой finding снимается как дубль; условные findings привязаны к исходным; защита у одного и finding у другого — в `Conflicts` с правилом из README, без разрешения. Критерий: ни одного места в двух findings одной категории; все условные findings связаны.
- [ ] **Stage E — Проверка полей.** Четыре проверки «поле есть или нет»: Evidence с файлом и строкой; сценарий по полю владельца; Confidence с основанием; severity P1–P3. Substitution test над Problem и Why it matters — пометка в строке `Pipeline:`, не основание для `Dropped`. Критерий: каждый finding итога прошёл четыре проверки; непрошедшие — в `Dropped` с причиной.
- [ ] **Stage F — Единый отчёт** по [REPORT.md](REPORT.md) в `<output-dir>/backend-review.md`.

## Режимы запуска

- **Полный** — все пять скиллов.
- **Частичный** — названное подмножество в том же порядке. Если у выбранного skill есть вход от невыбранного (dependency и domain — Architecture summary; persistence — ещё Dependency map и Domain summary; error handling — ещё Persistence summary), оркестратор говорит об этом до запуска и предлагает добавить недостающий skill или запустить в режиме «без отчёта» с пометкой в Scope. Без ответа — второй вариант.
- **Повторный** — те же скиллы после правок кода, новый `<output-dir>`. Отчёты предыдущего прогона передаются как справка с путём, входной моделью не являются; `Shared context` собирается заново.

Параллельный запуск не используется; заметка о возможных волнах — в PROTOCOL.md.

## Стоимость контекста

В контексте оркестратора живут только `Shared context`, пять блоков Scope + Summary, строки «Вне scope» (включая собранные `grep` изнутри findings) и Mismatches. Полные отчёты читаются с диска на Stage C–F, по разделам и по одному finding; пять полных отчётов одновременно в контексте не держатся.
