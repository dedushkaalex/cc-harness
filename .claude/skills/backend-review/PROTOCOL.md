# Протокол оркестратора

Справочник к стадиям из [SKILL.md](SKILL.md): что именно передаётся на каждой стадии, что проверяется и что делать при сбое. Ни одна проверка в этом файле не отвечает на вопрос «есть ли здесь проблема в коде» — на него отвечают только пять скиллов.

## Термины

- **`<target>`** — аргумент вызова: PR (`#42`, URL, `main...feature/x`), diff (staged, рабочее дерево, диапазон коммитов), модуль (путь), репозиторий (только явное слово `repo`).
- **`<output-dir>`** — каталог отчётов: по умолчанию `reviews/<YYYY-MM-DD>-<slug target>/` от корня репозитория; можно передать аргументом. Оркестратор создаёт его на Stage A и не добавляет в git: `reviews/` стоит в `.gitignore`, каталог по другому пути тоже остаётся вне коммитов.
- **Агент** — отдельный запуск skill в собственном контексте (Agent tool, `subagent_type: general-purpose`). Skill выполняется агентом целиком по своему SKILL.md; оркестратор видит только то, что агент вернул.
- **Строка handoff** — строка «Вне scope», строка внутри finding с именем другого skill как владельца («Вне scope: backend-persistence-review» в Trade-offs) или Mismatch из отчёта одного skill. **Вердикт** — запись владельца о том же месте: finding, Non-finding, existing protection или запись в разделе `Handoff verdicts`.
- **Место** — файл и строка или диапазон. Два места совпадают, если файл тот же и диапазоны пересекаются; строка без номера совпадает по файлу; строка без файла (назван компонент) — по упоминанию того же компонента в Evidence.

## Stage A — Shared context

### Код под ревью

Правило соседей (Step 0 каждого skill), применяется один раз:

- PR или diff — изменённые файлы (`gh pr diff --name-only`, `git diff --name-only <base>...<head>`) плюс один шаг по графу вызовов: компоненты, которые изменённые файлы вызывают напрямую, и компоненты, которые вызывают их напрямую. Граф — по `.codegraph/`, если он есть, иначе по импортам и вызовам через поиск. Дальше одного шага не ходить.
- Модуль — все его файлы плюс один шаг наружу.
- Репозиторий — только по явному слову; тогда единица таблиц у скиллов — модуль, как в их REPORT.md.

Схема хранилища и миграции входят, если изменены или лежат в одном шаге. Результат — список путей и правило, по которому он получен. Граница фиксируется до конца прогона: скиллы, которые по своим правилам ищут обходные пути, обработчики или вторых writers по всему репозиторию, границу не расширяют; оркестратор — тоже.

### Контекст

Один проход по источникам в порядке надёжности из Step 0 соседей: ADR и `docs/`; README и CLAUDE.md; git log; тесты; конфиги окружений, docker-compose, манифесты k8s, CI; манифест зависимостей; конфигурация очередей и клиентов, документация providers. Собирается ровно то, что нужно всем или нескольким скиллам:

| Строка | Что записать | Кто использует |
|---|---|---|
| Известно / Не известно | утверждения о планах и ограничениях с источником; чего нет — «не известно» | все |
| Deployment model | число экземпляров, тип deploy (rolling / blue-green / stop-the-world), очереди и их гарантия доставки | persistence, error handling |
| Источники повторов | очереди at-least-once, повтор webhook, retry в клиентах, jobs по расписанию — с источником или «не известно» | persistence, error handling |
| Базовая единица | механизм объявления зависимости и источник; подмена в тестах | architecture, dependency |
| Базовая единица ошибки | механизм выражения отказа и источник | error handling |

Две базовые единицы не бывают «не известно»: определяются по объявлениям в коде под ревью и соседних модулях; при двух механизмах — оба и граница между ними. Лимит — один проход: нет ответа — «не известно», как у соседей.

Специфичное для одного skill — источники правил (domain), объёмы и гарантии хранилища (persistence), политики повторов, global handlers и контракт ошибок наружу (error handling) — оркестратор не собирает: skill дособирает это сам по своему Step 0 и помечает «дособрано».

Наблюдения о качестве кода, сделанные во время Stage A («controller открывает транзакцию», «catch пустой»), никуда не записываются. Они не контекст и не строка «Вне scope»: оркестратор не источник handoff.

### Формат

Блок записывается в `<output-dir>/shared-context.md` и вставляется в каждый промт агента как есть:

```text
## Shared context

Target: PR #42 (main...feature/refund) — режим: полный
Code under review: src/billing/**, src/http/billing.controller.ts, src/jobs/refund.job.ts
  (diff PR #42 плюс один шаг по графу вызовов; граница одна для всех скиллов)

Известно:    один transport (HTTP) плюс job возвратов — README, docker-compose
Известно:    два экземпляра API, rolling deploy — k8s/deployment.yaml, CI
Известно:    webhook оплаты повторяется до 5 раз при таймауте — docs/payments.md
Не известно: планируется ли второе хранилище — в источниках нет
Deployment model: два экземпляра, rolling deploy; очередь заказов at-least-once — infra/queue.yaml
Источники повторов: webhook оплаты — docs/payments.md; очередь заказов — infra/queue.yaml;
             retry в HTTP-клиенте платежей — не известно
Базовая единица: class + параметр конструктора, регистрация в DI — источник: все сервисы
             в src/; подмена в тестах: override provider, test/**/*.spec.ts
Базовая единица ошибки: исключение — источник: сценарии в src/** бросают и ловят, объявленных
             типов ошибок в сигнатурах нет; на границе — exception filter, src/main.ts:18
```

Формат совпадает с блоком Context в REPORT.md каждого skill: строки переносятся в Scope отчёта без переделки, ниже них skill дописывает «дособрано».

### Критерий

Файл `<output-dir>/shared-context.md` есть; в нём граница с правилом, список «известно / не известно» с источниками, deployment model, источники повторов и обе базовые единицы.

## Stage B — Последовательный запуск

### Порядок и вход

| Skill | Summary, который он отдаёт | Что получает на вход |
|---|---|---|
| `backend-architecture-review` | Architecture summary | Shared context |
| `backend-dependency-review` | Dependency map | + Scope и Architecture summary; строки «Вне scope» → dependency |
| `backend-domain-review` | Domain summary | + Scope и Summary двух предыдущих; строки «Вне scope» → domain |
| `backend-persistence-review` | Persistence summary | + Scope и Summary трёх предыдущих; строки «Вне scope» → persistence |
| `backend-error-handling-review` | Error-handling summary | + Scope и Summary четырёх предыдущих; строки «Вне scope» → error handling |

Строки «Вне scope» адресуются по имени владельца в строке. Строки внутри findings с именем владельца агент не возвращает, поэтому перед запуском каждого skill они собираются с диска: `grep -n 'backend-<x>-review'` по разделу Findings каждого отработавшего отчёта (между `## Findings` и следующим заголовком `##`); место такой строки — Evidence finding под ближайшим заголовком `###` выше. Собранные строки передаются вместе со строками «Вне scope»; текст finding при этом не читается. Mismatches на Stage B не передаются: их владелец всегда уже отработавший skill, они закрываются на Stage C.

Полные findings предыдущих отчётов не передаются. Skill, которому нужно конкретное место, читает его сам из `<output-dir>/<skill>.md`; путь есть в промте.

### Промт агента

```text
Ты выполняешь skill `backend-<x>-review` как шаг pipeline `backend-review`.

1. Загрузи skill `backend-<x>-review` через Skill tool (если недоступен — прочитай
   `.claude/skills/backend-<x>-review/SKILL.md` и файлы, на которые он ссылается)
   и выполни его целиком, все шаги.
2. Shared context ниже — это Context для Step 0 и граница кода под ревью. Не собирай
   заново; дособери только то, что нужно этому skill и чего здесь нет, пометь «дособрано».
   Границу не расширяй: модули, найденные вне неё, оцениваются по правилам skill,
   но в Code under review не попадают.
3. Входные модели — блоки Scope и Summary предыдущих отчётов, ниже. Это модель для
   проверки, не факт; противоречия — в Mismatches блока Scope. Полные отчёты лежат в
   `<output-dir>/<skill>.md`; читай оттуда только конкретное место, если оно нужно.
4. Строки, адресованные тебе, — ниже. Каждая получает вердикт с тем же файлом и строкой:
   finding, Non-finding или existing protection. Если в шаблоне твоего REPORT.md нет
   раздела для такого вердикта, запиши его в раздел `## Handoff verdicts` в конце отчёта.
5. Полный отчёт по своему REPORT.md запиши в `<output-dir>/backend-<x>-review.md`.
6. В ответ верни только: блок Scope, блок <Summary>, раздел «Вне scope», раздел
   `Handoff verdicts`, если он есть, и счётчики: findings по severity, Non-findings,
   записи в разделе защит. Ничего больше — findings целиком не возвращай.

## Shared context
<блок из shared-context.md>

## Входные модели
<Scope + Summary каждого предыдущего отчёта по порядку; для пропущенного —
«отчёт backend-<y>-review отсутствует: <причина>; работай без него и укажи это в Scope»>

## Строки, адресованные этому skill
<строки или «нет»>

## Справка (только повторный режим)
Отчёт предыдущего прогона: `<prev-dir>/backend-<x>-review.md` — не входная модель.
```

### Раздел `Handoff verdicts`

Пишет только сам skill, в конце своего отчёта после «Вне scope», и только при запуске через `backend-review`; вне pipeline раздела нет — так записано в REPORT.md каждого skill. Одна строка на место, в порядке полученных строк:

```text
## Handoff verdicts

- `path:line` — <фраза строки handoff> (из `backend-<y>-review`, Вне scope | Mismatch) —
  finding: [Px] «название» | Non-finding: <причина> | existing protection: <причина> |
  подтверждён: <исправленная строка модели> | отклонён: <причина>
```

Finding как вердикт пишется в Findings по шаблону skill, здесь — только ссылка на него. В итоговый отчёт вердикты попадают по статусу closed: finding — через Findings после Stage D–E, existing protection — строкой в Existing protections с тегом владельца, Non-finding — в счётчик Non-findings владельца, «подтверждён» и «отклонён» — в счётчик closed таблицы Scope.

### Проверка на выходе

Проверяется протокол, не содержание:

1. файл `<output-dir>/backend-<x>-review.md` существует;
2. в нём блок Scope с `Code under review`, и граница совпадает с Shared context; расхождение записывается в итоговый Scope как есть, findings из-за него не снимаются;
3. есть раздел Summary этого skill и раздел «Вне scope» (может быть «не найдено»);
4. у каждой строки «Вне scope» назван владелец или «владелец не назначен»; строка без владельца передаётся дальше как «владелец не назначен».

Внутри findings оркестратор на этой стадии читает только строки с именем другого skill — `grep` для следующего запуска; текст findings не читает.

### Сбой

Сбой — агент завершился ошибкой, файла нет, нет блока Scope или Summary. Один повтор с тем же промтом. Второй сбой — skill пропущен: следующие получают вместо его блоков строку «отчёт отсутствует: <причина>», в их Scope это отмечено, в итоговом отчёте — раздел `Skipped`. Строки handoff, адресованные пропущенному skill, на Stage C не закрываются: статус unresolved с причиной «владелец пропущен».

### Критерий

Пять файлов отчётов в `<output-dir>` или явные записи о пропуске; в контексте оркестратора — только Scope, Summary, «Вне scope» и счётчики каждого.

## Stage C — Замыкание handoff

### Сбор

Из всех отчётов: раздел «Вне scope», Mismatches блока Scope, строки внутри findings с именем другого skill как владельца. Каждая строка получает: источник, место, одну фразу, владельца. Читаются только эти разделы — `grep -n` по именам скиллов и по заголовкам, не файл целиком.

### Что считается вердиктом

В отчёте владельца есть запись о том же месте (по правилу совпадения из Терминов) в одном из разделов: Findings (по Evidence), Non-findings, раздел защит (`Good decisions`, `Good dependencies`, `Protected invariants`, `Existing protections`), `Handoff verdicts`. Для Mismatch — запись в `Handoff verdicts` владельца: «подтверждён: <исправленная строка модели>», «отклонён: <причина>» или finding.

Проверка — `grep -n` по файлу места в отчёте владельца; раздел — по ближайшему заголовку `##` выше. Оркестратор проверяет, что вердикт есть, а не что он верен.

### Адресный проход

Строки без вердикта группируются по владельцу. Один запуск на владельца:

```text
Ты выполняешь skill `backend-<x>-review` в адресном режиме pipeline `backend-review`.
Загрузи skill (Skill tool или SKILL.md) и его REPORT.md. Дай вердикт на N мест ниже —
finding по шаблону REPORT.md, Non-finding с причиной, existing protection с причиной;
для Mismatch — «подтверждён» с исправленной строкой модели или «отклонён» с причиной.
Другой работы не делай: остальной код не смотри, новых строк «Вне scope» не пиши.
Shared context и твой отчёт: `<output-dir>/shared-context.md`,
`<output-dir>/backend-<x>-review.md`. Допиши в конец своего отчёта раздел
`## Handoff verdicts` (если он есть — дополни), остальной текст отчёта не меняй.
Верни только этот раздел.

## Места
- `path:line` — <фраза> (из `backend-<y>-review`, Вне scope | Mismatch)
```

Один адресный проход на skill за прогон. Что после него без вердикта — `Unresolved handoffs`. Новые строки «Вне scope», появившиеся в адресном проходе вопреки инструкции, второй проход не получают: `Unresolved handoffs` с пометкой «появилась в адресном проходе».

### Статусы

- **closed** — вердикт найден; в итоговом Scope учтён счётчиком, сам вердикт попадает в итог через Findings, Existing protections или счётчик Non-findings.
- **unresolved** — вердикта нет после адресного прохода; владелец пропущен; владелец не запускался (частичный режим).
- **not assigned** — «владелец не назначен»; в итоговый отчёт как есть, раздел «Вне scope».

### Критерий

У каждой собранной строки один из трёх статусов; unresolved — с причиной.

## Stage D — Дубли и конфликты

### Одно место в двух findings

Пары findings с совпадающим местом ищутся по Evidence (`grep -n` путей по пяти отчётам). Для каждой пары:

1. Категория каждого finding определяется по его Problem и по правилу разделения пары из README: исправление переносит код — architecture; убирает import, меняет тип, переворачивает стрелку — dependency; вызывает или создаёт владельца правила — domain; меняет, как state пишется и читается, — persistence; меняет, что узнаёт вызывающий, — error handling.
2. Оба finding в одной категории — дубль. Остаётся finding владельца по матрице; чужой в итог не входит, а записывается под finding владельца строкой «дубль снят: `<skill>` описал то же место как [Px] „…“» — это и есть его строка «Вне scope» с пометкой «уже описан у владельца». Severity и Confidence — владельца, даже если у дубля уровень был выше.
3. Категории разные, и каждый finding в категории своего автора — не дубль: README назначил обе стороны разным владельцам («транзакция лежит не там — architecture; покрывает ли обе записи — persistence»). Оба остаются, каждый получает перекрёстную ссылку «то же место с другой стороны: [Px] `<skill>`».
4. Категорию определить однозначно нельзя — оба остаются с перекрёстной ссылкой, и в `Conflicts` строка «владелец по матрице не определён» с обеими позициями.

Finding в чужой категории без пары у владельца — не дубль и не предмет этой стадии: оркестратор не переназначает findings и не судит, чья это категория.

### Условные findings

Finding с пометкой «при условии применения [Px] `<skill>`» привязывается к исходному finding по severity и по месту из Evidence («`order.controller.ts:31-58` → переносится в `OrderService`»). В итоге он помечается «зависит от [Px] `<skill>` „название“». Если исходный finding не находится однозначно — в пометке перечисляются кандидаты. Если исходный finding попал в `Dropped` или снят как дубль — ссылка ведёт на то, что осталось, и пометка это называет. Зависимый finding не снимается и не понижается.

### Конфликты

Конфликт — одно место у одного skill в разделе защит, у другого в Findings, и finding **отрицает** то, что защита утверждает: «заказ и резерв в одной транзакции — сохранить» против «резерв пишется вне транзакции заказа». Finding, который опирается на защиту как на предпосылку («правило защищено на каждом пути, но хранилище его не держит»), — не конфликт, а дополнение: перекрёстная ссылка, как в п. 3 выше.

Конфликт не разрешается. В `Conflicts` записываются обе позиции дословно с именем skill и раздела и правило из таблицы «Boundaries that need a splitting rule» README, которое должно было это разрешить. Обе записи остаются на своих местах в итоге: finding в Findings, защита в Existing protections, каждая с пометкой «см. Conflicts».

### Критерий

Ни одного места в двух findings одной категории; у каждого условного finding есть ссылка на исходный или список кандидатов; каждый конфликт записан с обеими позициями и правилом.

## Stage E — Проверка полей

Четыре проверки на каждый finding, вошедший в итог после Stage D, включая findings из `Handoff verdicts`. Каждая отвечает на вопрос «поле есть или нет», не «поле верно»:

| # | Проверка | Что должно быть |
|---|---|---|
| 1 | Evidence | хотя бы одно место с файлом и строкой |
| 2 | Сценарий | поле сценария владельца заполнено: architecture — Why it matters называет изменение, которое станет дорогим; dependency — Change scenario; domain — How it can be violated; persistence — Failure scenario; error handling — Failure scenario |
| 3 | Confidence | уровень high / medium / low и основание после него |
| 4 | Severity | P1, P2 или P3 в заголовке; уровень выбран владельцем и не пересматривается |

Finding, не прошедший любую проверку, — в `Dropped` с номером проверки и причиной; в Findings он не входит, в отчёте владельца остаётся. Оркестратор не дописывает недостающее поле сам: если Evidence нет, его нет.

### Substitution test — пометка, не проверка

«Substitution test» из README над готовым текстом: в Problem и Why it matters названия framework, ORM, библиотек, драйверов, engine заменяются на роль («ORM», «хранилище», «очередь»). Если фраза после этого перестаёт называть проблему, в строку `Pipeline:` этого finding добавляется «substitution test: сомнительно, см. владельца». Finding остаётся в Findings с уровнем и текстом владельца: результат теста — суждение о содержании, ложное «не прошёл» сняло бы настоящий finding, а по правилу на границе из SKILL.md это не работа оркестратора. Название технологии само по себе пометку не даёт: «транзакция Prisma лежит в handler» после замены остаётся проблемой, «query должна быть внутри `$transaction`» — нет. Переписанный текст никуда не записывается.

### Критерий

Каждый finding в Findings итогового отчёта прошёл четыре проверки; каждый непрошедший — в `Dropped`; у каждого сомнительного по substitution test — пометка в `Pipeline:`.

## Stage F — Единый отчёт

Шаблон и правила слияния — в [REPORT.md](REPORT.md). Отчёт пишется в `<output-dir>/backend-review.md`; пользователю возвращается он же. Оркестратор добавляет к тексту владельцев только теги владельца, ссылки, строки `Pipeline:` и статусы; ничего в полях finding не меняет.

## Стоимость контекста

В контексте оркестратора живут: Shared context; пять блоков Scope + Summary; строки «Вне scope» и строки handoff, собранные `grep` изнутри findings; Mismatches и счётчики. Полные отчёты читаются с диска только на Stage C–F и только нужными частями: разделы — по заголовкам (`awk '/^## Findings/,/^## Good/'`), места — `grep -n` по пути, findings на Stage E и F — по одному. Пять полных отчётов одновременно в контексте не держатся.

## Параллельный запуск

Сейчас не используется. После стабилизации возможны три волны: `architecture → {dependency, domain} → persistence → error handling` — при условии, что domain-review не берёт ничего из Dependency map (сейчас его вход — только Architecture summary), и с обязательным адресным проходом на Stage C, потому что параллельные скиллы не видят «Вне scope» друг друга.

## Чего оркестратор не делает никогда

Перечитать перед сдачей отчёта:

- не добавляет finding «который все пропустили» — место без вердикта владельца идёт в `Unresolved handoffs`, не в Findings;
- не меняет severity, confidence, текст Problem, Evidence, рекомендации;
- не расширяет код под ревью «раз уж смотрим»;
- не переписывает файлы отчётов скиллов — дописать раздел `Handoff verdicts` может только сам skill в адресном проходе;
- не разрешает конфликт и не выбирает «правильную» позицию;
- не даёт вердикт non-finding вместо владельца;
- не снимает finding по substitution test — сомнение записывается пометкой в `Pipeline:`, finding остаётся;
- не решает, чья категория, когда матрица не даёт ответа, — записывает обе позиции.
