# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага.

## Step 0 — Code under review и контекст

**С отчётом architecture-review** — граница кода под ревью и блок Context берутся из его блока Scope. Таблица компонентов даёт две вещи, нужные дальше: список entry points (transport-компоненты, обработчики очередей, jobs, CLI) и список тех, кто пишет в persistence (колонка «использует»). Дособирай только источники правил, перечисленные ниже.

**Без отчёта** — определи код под ревью сам: diff или названные файлы плюс один шаг по графу вызовов; модуль целиком плюс один шаг наружу; весь репозиторий — только если сказано явно.

**Особенность этого skill.** Обходной путь редко лежит в одном шаге от проверяемого кода. Поэтому на Step 3 записи защищаемого state ищутся по всему репозиторию поиском по имени поля, таблицы, статуса или типа, а не только в коде под ревью. Найденный так модуль **не** становится кодом под ревью: в нём проверяется только одно — пишет ли он этот state и проходит ли через правило. Всё остальное в нём не оценивается.

**Источники правил**, в порядке надёжности:

1. документы о предметной области — ADR, `docs/`, README: прямые формулировки правил и планов;
2. описание изменения — PR, issue, commit message: какое правило вводится или меняется;
3. тесты — названия и сценарии часто и есть формулировки правил: «нельзя отменить отправленный заказ»;
4. схема хранилища и миграции — `CHECK`, `UNIQUE`, `NOT NULL`, foreign key, enum-типы: invariants, которые гарантирует хранилище;
5. схемы валидации на границах (DTO, form, changeset, схема запроса) — evidence того, где проверка есть, а не источник правил: там обычно input validation.

Итог — список «известно / не известно» и список источников правил:

```text
Известно:    заказ нельзя отменить после отправки — docs/orders.md, test/orders/cancel.test.ts
Известно:    баланс не бывает отрицательным — CHECK balance >= 0 в migrations/004, ADR-0003
Не известно: планируется ли второй канал изменения баланса (импорт) — в источниках нет
Источники правил: docs/orders.md, ADR-0003, test/orders/**, migrations/**
```

Не ищи дольше одного прохода: нет ответа — «не известно», в finding это допущение с Confidence не выше medium.

## Step 1 — Domain concepts

Concept имеет бизнес-смысл, когда есть хотя бы одно из evidence:

- назван в документах, тестах или описании изменения как понятие предметной области;
- к нему привязано правило — проверка в коде, constraint в схеме, тест;
- у него есть lifecycle — статус, стадия, флаг активности, который меняется по правилам;
- это деньги, количество, срок, лимит, право участника;
- от него зависит решение в коде — ветвление перед записью, выбор сценария.

Не concept: поле с одной только проверкой формата, технический идентификатор без правил, конфигурация, метрики, логи. Тип или класс не становится concept потому, что он есть.

Где искать представление: тип, структура, схема ORM или persistence, таблица, enum, набор строковых литералов, поле другого concept. Название framework-конструкции — evidence, где concept записан, и не более.

Итог — таблица:

| Concept | Где представлен | Почему бизнес-понятие |
|---|---|---|
| `Account.balance` | `account.ts:8`, колонка `accounts.balance` | ADR-0003: не бывает отрицательным; `CHECK` в `migrations/004` |
| `Order.status` | enum в `order.ts:3`, enum-тип в схеме | lifecycle из пяти статусов, `test/orders/**` |

Лимит — 15 строк; дальше группируй по модулям.

## Step 2 — Business rules

Правило определяет допустимое поведение системы в терминах предметной области: «перевод не превышает доступный баланс», «у пользователя не бывает двух активных подписок», «просроченная сессия не считается активной», «скидка применяется только к товарам из категории».

Где искать: условия перед записью state; ошибки с бизнес-смыслом (`InsufficientFunds`, `OrderAlreadyShipped`); constraints схемы; тесты; документы.

Три фильтра, через которые проходит каждый кандидат:

- **Input validation** — проверка формы значения без обращения к другому state: формат email, обязательное поле, диапазон длины. Не правило. «Подтверждённый email нельзя менять без отдельной процедуры» — правило, потому что зависит от state.
- **Orchestration** — последовательность шагов без решения: загрузить, сохранить, отправить письмо. Не правило. «Счёт не может стать отрицательным» — правило. Где лежать orchestration, решает `backend-architecture-review`.
- **Authorization** — кто может вызвать операцию: роль, токен, scope, единообразно на входе. Владелец не назначен, в «Вне scope». «Отменить заказ может только его владелец, пока заказ не отправлен» — правило: зависит от state объекта и участника.

Правило записывается одной фразой на языке предметной области, без имён функций и типов, с источником. Правило, у которого источника нет ни в коде (проверка, constraint, тест), ни в документе — открытый вопрос для Domain summary: «похоже, подразумевается, что …; подтверждения нет». В findings оно не попадает.

Лимит — 20 правил; дальше отбирай те, что защищают деньги, права, необратимые операции и данные, на которые опираются другие правила.

## Step 3 — Owner и пути

Для каждого правила из Step 2 ответь письменно:

1. **Какой state защищает** — поле, таблица, тип, связь: `Account.balance`, `Order.status`, пара `(user_id, active)` в подписках.
2. **Где проверяется** — файл и строка каждой проверки. Проверкой считается и constraint хранилища, и тип, который не даёт построить значение.
3. **Все пути записи этого state.** Путь — любое место, где значение записывается: вызов записи в хранилище, присваивание поля, конструктор или фабрика, bulk-операция, обработчик очереди, job по расписанию, admin-команда, CLI, миграция данных, seed для окружений, кроме локальной разработки. Ищи по всему репозиторию: имя поля, имя таблицы, значения статуса, имя типа. Для каждого пути — вход, из которого он вызывается.
4. **Какие пути проходят через проверку, какие нет.**

Владелец правила есть, когда есть одно место, через которое проходят все записи state, и правило проверяется там или до него на каждом пути. Владельцем может быть функция, метод, модуль, тип с единственным конструктором, constraint хранилища. Отдельный domain layer не требуется. Владельца нет, когда проверка лежит в вызывающих, а записывать state может каждый из них.

Итог — таблица:

| Правило | State | Владелец | Через владельца | В обход |
|---|---|---|---|---|
| баланс не отрицательный | `accounts.balance` | `CHECK` в `migrations/004` | все записи в таблицу | — |
| перевод не превышает баланс | `accounts.balance` | `transfer.ts:40` | `transfer.ts` | `refund.ts:22` — пишет balance без проверки; вход: `POST /refunds` |

Constraint хранилища — полноценный владелец, если все пути пишут в это хранилище. Что при нарушении constraint приложение отдаёт техническую ошибку вместо бизнес-ответа — не тема этого skill: «Вне scope», владелец `backend-error-handling-review`.

**С отчётом architecture-review.** Если его finding переносит проверку из одного компонента в другой, таблица строится по состоянию после переноса. Если после переноса какой-то путь перестаёт проходить через проверку, это записывается как обход с пометкой «при условии применения [Pn] architecture-review».

## Step 4 — Invariants

Кандидат — каждая строка «в обход» из таблицы Step 3. Finding появляется только после доказательства достижимости:

1. **Вход существует** — обходная запись вызывается из entry point в коде: handler, обработчик очереди, job, команда. Функция, которую никто не вызывает, — не путь.
2. **Значение может быть недопустимым** — на этом пути выше по стеку нет той же проверки. Если проверка стоит у вызывающего, путь защищён, а владелец правила — вызывающий: это запись в Protected invariants с пометкой «защита в вызывающем; второй вызывающий должен повторить проверку», максимум P3 и только при втором вызывающем в планах (источник — Context).
3. **Состояние недопустимо по правилу** — назови, каким станет state: «balance = -300», «две активные подписки у одного пользователя».

Типовые частичные защиты: проверка при создании, но не при обновлении; при обновлении одной записи, но не в bulk-операции; в основном сценарии, но не в импорте, откате или admin-операции; в приложении, но второе приложение или job пишут в ту же таблицу.

Не finding: гипотетический вызов; тест, пишущий state напрямую; seed для локальной разработки; путь, который не может получить недопустимое значение по построению. Каждый отброшенный кандидат — строка в Non-findings с причиной, чтобы следующий ревьюер не искал заново.

## Step 5 — Duplicated rules

Дублирование — одна и та же проверка одного и того же state с одним и тем же бизнес-смыслом в независимых местах: три сценария сами сравнивают `balance` с суммой; handler, сервис и job каждый проверяют, что подписка активна, своим кодом.

Для каждой пары ответь:

1. **Это одно правило?** Один бизнес-вопрос, один state. «Достаточно ли средств» в переводе и в выводе — одно правило. «Активна ли подписка» для доступа и «можно ли продлить» — разные, хотя оба смотрят на `status`.
2. **Различие контекстное?** Разные участники, стадии, лимиты — разные правила, не дублирование.
3. **Что придётся править при изменении правила?** Список файлов. Если один — дублирования нет.
4. **Может ли копия устареть?** Копии независимы, если у них нет общего источника: каждая написана своим кодом.

Не дублирование: повторение технических проверок (null, формат, обязательность); проверка на границе плюс та же проверка у владельца, если пограничная **вызывает** владельца или явно объявлена как ранний ответ, а владелец — единственный источник правила. Две независимые реализации одного предиката — дублирование, даже если одна из них «для быстрого ответа».

Решение — один владелец: функция, метод или тип, который знает правило, и вызов его из остальных мест. Дублирование, вызванное представлением concept (Step 7), записывается одним finding с указанием причины.

## Step 6 — State transitions

Для concept с lifecycle восстанови допустимые переходы из кода, а не из головы: значения статуса (enum, литералы, enum-тип хранилища), проверки текущего статуса перед сменой (`if status != pending → error`), тесты, документы.

```text
pending → paid → shipped → delivered
pending → cancelled
paid → cancelled (возврат)
```

Затем найди **все записи статуса** — так же, как на Step 3: присваивания, обновления в хранилище, bulk-операции, jobs, импорт, admin. Для каждой ответь: проверяется ли исходный статус перед записью? Запись без проверки исходного статуса — кандидат.

Finding — только достижимый недопустимый переход: есть вход, через который объект в статусе `delivered` получает `pending`, или `cancelled` получает `paid`. Назови вход, запись и переход.

Защищённые варианты, которые фиксируются в Protected invariants: одна функция перехода с таблицей допустимых пар; тип, у которого операции доступны только из нужного статуса; constraint или trigger хранилища, если все пути пишут туда. Строковый статус при такой функции — не finding.

## Step 7 — Primitive concepts

Для каждого значимого concept, представленного общим типом (число, строка, идентификатор без типа), ответь: **какое правило ограничивает это значение?**

- Правила нет — primitive достаточен, в findings не попадает.
- Правило проверяется один раз при построении, и значение потом не меняется в обход — защищено, Protected invariants.
- Правило проверяет каждый consumer сам — это дублирование (Step 5) или пропуск на одном из путей (Step 4), причина которых — представление. Один finding, в поле Problem названа причина; второго finding «primitive» не бывает.
- Недопустимое значение строится без усилий и записывается в state — пропуск из Step 4 с той же причиной.

Value Object не предлагается автоматически. Если finding есть, минимальные решения от дешёвого к дорогому: функция-конструктор, которая одна знает правило и возвращает проверенное значение; тип с единственным способом построения (закрытый конструктор, непрозрачный тип, newtype, branded type, структура с приватным полем); enum вместо строки для замкнутого набора значений. В каждом стеке это выражается своими средствами, и в Suggested solution способ называется как пример, а не как требование.

## Step 8 — Recommendations и substitution test

Для каждого finding — минимальное изменение, порядок от дешёвого к дорогому:

1. вызвать существующего владельца из обходного пути;
2. собрать правило в одном месте, через которое проходят все записи state, и вызывать его из всех путей;
3. инкапсулировать переход статуса в одной функции с таблицей допустимых переходов;
4. ввести тип или функцию-конструктор, которые не дают построить недопустимое значение;
5. ограничить способы записи state — единственная функция записи, закрытое поле, граница модуля.

Полный редизайн под DDD, новый слой, Aggregate или Repository ради чистоты не предлагаются. Новая abstraction оправдана только правилом из finding, которое она защищает.

К каждой рекомендации четыре пункта:

1. **Какое правило защищено плохо** — ссылка на evidence.
2. **Как его можно нарушить** — вход, обходная запись, недопустимое состояние.
3. **Как изменение это закрывает** — какие пути после изменения проходят через владельца.
4. **Какую complexity добавляет** — новый тип, файл, обязательный вызов, миграция существующих данных.

Если изменение дороже проблемы — «оставить как есть», источник из Context и при каком изменении вердикт поменяется.

**Substitution test** для каждого finding перед записью в отчёт. Перепиши Problem, How it can be violated и Why it matters без названий framework, ORM, библиотек и папок. Представь тот же backend на другом стеке — как минимум на трёх из: NestJS, FastAPI, Phoenix, Go, Rust, Spring, .NET, Effect. Если finding исчезает — его не было: «модель ORM содержит логику», «нет Entity», «в этом стеке правило должно лежать в Service» — не findings. Если меняются только Evidence и способ реализации в Suggested solution — finding настоящий. Структура папок и имена компонентов ничего не доказывают: правило защищено не потому, что лежит в `domain/`, и не обходится потому, что лежит в `controllers/`.
