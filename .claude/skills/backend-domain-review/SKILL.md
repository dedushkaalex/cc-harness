# Backend domain review

## Primary question

> Где живёт это бизнес-правило, кто отвечает за его соблюдение, и есть ли путь изменить state в обход него?

**Finding принадлежит этому skill**, когда проблема в самом правиле, а не в том, где лежит код: существующий путь меняет state без проверки, которую делает другой путь; одно правило реализовано в трёх независимых местах; недопустимый переход статуса достижим из кода; значимый concept представлен так, что недопустимое значение строится без усилий.

**Исправления** в этом skill меняют то, кто и где защищает правило: вызвать существующего владельца из обходного пути, собрать правило в одном месте, через которое проходят все изменения state, инкапсулировать переход, ввести тип или функцию-конструктор, которые не дают построить недопустимое значение, ограничить способы записи state. Проверка: если исправление — перенести код чужого слоя в свой слой, не меняя, какие пути проходят через правило, finding не отсюда, это `backend-architecture-review`; если исправление — убрать import или заменить чужой тип, это `backend-dependency-review`.

Не спрашивай «использует ли проект DDD» и «есть ли здесь Entity, Value Object, Aggregate». Спрашивай, какие правила существуют, где они лежат, кто их защищает и может ли система оказаться в недопустимом состоянии. Правило может жить в функции, сервисе, типе, модуле или constraint базы данных: владелец есть, если есть одно место, через которое проходят все изменения защищаемого state.

## Do NOT evaluate

Владелец — `backend-architecture-review`:

- лежит ли в компоненте не тот вид работы, в том числе бизнес-правило внутри repository, handler или клиента внешнего API;
- слишком ли много видов работы в одном компоненте;
- слой компонента: с отчётом на входе слой берётся из его таблицы.

Владелец — `backend-dependency-review`:

- импорты, направление зависимостей, coupling, cycles;
- leakage типов и ошибок через границы, в том числе persistence-тип в domain-сигнатуре;
- нужен ли contract, port, adapter, dependency inversion.

Владелец — `backend-persistence-review`: transaction boundaries и atomicity, concurrency, constraints хранилища, стоимость запросов, idempotency записей, совместимость миграций.

HTTP/API design, механика authentication и authorization (роли, токены, scopes, кто может вызвать endpoint), error handling, тесты, performance вне persistence — другие skills, когда появятся; пока такие места уходят в «Вне scope» с названием категории и пометкой «владелец не назначен».

**Правило разделения с architecture-review:** тот skill спрашивает, тот ли вид работы лежит в компоненте; этот — можно ли обойти правило. Правило лежит не в своём слое, но через него проходят все пути — architecture-review, здесь оно попадает в Protected invariants. Правило лежит в своём слое, но хотя бы один существующий путь его обходит — здесь.

**Правило разделения с dependency-review:** тип меняется, чтобы компонент перестал знать технологию или другой компонент — dependency-review; тип меняется, чтобы недопустимое значение нельзя было построить — здесь.

**Правило разделения с persistence-review:** здесь — есть ли правило и проходит ли через него каждый путь; там — держит ли хранилище правило, когда все пути через него проходят, но операции выполняются параллельно, повторно или частично. Один путь не проверяет — здесь. Все проверяют, а два параллельных вызова проходят проверку по одному снимку — там.

Примеры на границе:

- repository содержит правило «просроченный заказ не возвращать», и все чтения заказов идут через него — **не здесь**: бизнес-правило в persistence, владелец architecture-review; правило при этом защищено.
- три сценария проверяют `balance >= amount`, четвёртый (refund) пишет balance без проверки; все четыре лежат в application — **здесь**: invariant обходится существующим путём, слой ни при чём.
- application-сценарий возвращает тип ORM — **не здесь**: dependency-review.
- `amount` хранится как число, и три consumers каждый сам проверяют `amount > 0` — **здесь**: правило размазано по consumers из-за представления concept.
- `status` хранится строкой, но все переходы идут через одну функцию с таблицей допустимых переходов — **не finding**: primitive без обхода; запись в Protected invariants.
- handler проверяет роль вызывающего, сценарий проверяет, что отменяет владелец заказа и заказ не отправлен — **не дублирование**: первое — authorization (владелец не назначен), второе — бизнес-правило, здесь.

Всё замеченное вне scope — одной строкой в разделе «Вне scope» с именем skill-владельца.

## Ключевой вопрос для severity

> Какое недопустимое состояние система может принять, и через какой существующий путь?

Finding существует только с названным путём: файл и строка записи, которая меняет state в обход правила, и вход в неё из кода под ревью. «Repository публичный, его может вызвать кто угодно» — не путь. Гипотетический вызов, тест, который пишет state напрямую, seed для локальной разработки — не пути.

## Rule vs evidence

Framework, ORM, библиотека и структура папок — только evidence того, где правило записано и как устроена запись state. Архитектурный вывод от них не зависит: «persistence representation не должна быть единственным местом правила, если из-за этого правило не защищено на других путях» — правило; «модель ORM не должна содержать бизнес-логику» — не правило. Не предполагай наличие Controller, Service, Repository, Entity, UseCase, Module, Context, domain layer, application layer или DI. Проверка каждого finding: замени стек на FastAPI, Phoenix, Go или другой — если finding исчезает, его нет; если меняются только evidence и способ исправления, finding настоящий. Поля Problem, How it can be violated и Why it matters пишутся без названий framework и библиотек; названия допустимы в Evidence и в Suggested solution как пример реализации.

## Вход

С отчётом `backend-architecture-review` на входе его таблица компонентов — **исходная модель**: имена, слои и колонка «использует» показывают entry points и тех, кто пишет в persistence; компоненты заново не классифицируются. Его блок Context — источник сведений о планах. Противоречие с моделью записывается в раздел Mismatches блока Scope с владельцем architecture-review. Если перенос кода из finding architecture-review меняет, какие пути проходят через правило, оценивается состояние **после** переноса, finding помечается «при условии применения [P2] architecture-review»; перенос, который создаёт обход, записывается так же, чтобы рекомендацию можно было поправить. Без отчёта — Step 0 выполняется самостоятельно по STEPS.md, и в блоке Scope это указано.

## Порядок работы

Подробные вопросы для каждого шага — в [STEPS.md](STEPS.md). Шаг закрыт, когда выполнен его критерий.

- [ ] **Step 0 — Code under review и контекст.** Взять из отчёта architecture-review или собрать по STEPS.md; дособрать источники правил: документы, описание изменения, тесты, constraints в схеме хранилища. Критерий: в блоке Scope названы граница кода под ревью, список «известно / не известно» с источниками и список источников правил.
- [ ] **Step 1 — Domain concepts.** Выдели concepts с бизнес-смыслом, подтверждённым evidence. Критерий: таблица concept — где представлен — почему это бизнес-понятие; типы без правил и без роли в решениях в таблицу не попали.
- [ ] **Step 2 — Business rules.** Выдели правила допустимого поведения и отдели их от input validation, orchestration и authorization. Критерий: у каждого правила одна фраза на языке предметной области и источник в коде или документе; правило без источника записано как открытый вопрос, не как правило.
- [ ] **Step 3 — Owner и пути.** Для каждого правила: какой state защищает, где проверяется, все пути записи этого state, какие из них проходят через проверку. Критерий: таблица правило — state — владелец — пути через владельца — пути в обход, каждый путь с файлом и строкой.
- [ ] **Step 4 — Invariants.** Для каждого пути в обход докажи достижимость из кода. Критерий: у каждого finding названы вход, обходная запись и недопустимое состояние; недоказанные обходы записаны в Non-findings с причиной.
- [ ] **Step 5 — Duplicated rules.** Найди одно правило в независимых местах. Критерий: для каждой пары подтверждено, что это одно правило, а не контекстное различие или техническая проверка; названо, что придётся править при изменении правила.
- [ ] **Step 6 — State transitions.** Для concepts с lifecycle восстанови допустимые переходы и проверь записи статуса. Критерий: таблица переходов; finding только для недопустимого перехода, достижимого существующим путём.
- [ ] **Step 7 — Primitive concepts.** Для значимых concepts, представленных primitive, ответь, какое правило из-за этого нарушается или размазывается. Критерий: primitive без такого правила в findings не попал; primitive, который стал причиной finding из Step 4 или 5, записан как причина того же finding, а не как второй.
- [ ] **Step 8 — Recommendations и substitution test.** Для каждой проблемы минимальное изменение и проверка на смену стека. Критерий: у каждой рекомендации названы правило, способ нарушения, как изменение его закрывает и какую complexity добавляет; в Problem и Why it matters нет названий framework.
- [ ] **Отчёт** по шаблону из [REPORT.md](REPORT.md), с блоком Scope.

## Правила для findings

- Каждый finding опирается на конкретный код: путь к файлу и строка для правила и для обходного пути. Без evidence finding не существует.
- Правило подтверждается кодом (проверка, constraint, тест) или документом. Правило, которое ревьюер вывел из здравого смысла, не подтвердив ни тем, ни другим, в findings не попадает — только в Domain summary как открытый вопрос.
- У каждого finding есть **Confidence** — high / medium / low — с основанием: чем подтверждено правило и чем доказан путь; подробнее в REPORT.md.
- Severity — по последствиям недопустимого состояния, не по вкусу. P1 — критический invariant нарушается через существующий путь. P2 — дублирование или некритический обход. P3 — неявное правило с реальным риском при сопровождении. Предпочтение DDD или архитектурный вкус — не finding.
- Orchestration («загрузить, сохранить, отправить письмо») — не domain logic; где ей лежать, решает architecture-review.
- Простая domain model — не finding. Entity, Value Object, Aggregate, Domain Service, Factory, Repository не предлагаются ради чистоты: новая abstraction оправдана только правилом, invariant или переходом, которые она защищает и которые названы в finding.
- Защищённые правила фиксируются так же обязательно, как проблемы: следующий ревьюер должен знать, что трогать не нужно.
