# Вопросы для каждого шага

Справочник к порядку работы из [SKILL.md](SKILL.md). Открывай нужный раздел, когда дошёл до шага.

## Step 0 — Code under review и контекст

**С `Shared context` от оркестратора `backend-review`** — брать его как Context, не собирать заново, дособирать по правилам ниже только то, чего в нём нет; граница кода под ревью — из него.

**С отчётами на входе** — граница кода под ревью и блок Context берутся из блока Scope отчёта architecture-review. Таблица компонентов даёт entry points и слои. Dependency map даёт места, где тип ошибки уже пересекает границу слоя: здесь это подсказка, где искать точку преобразования, а не finding. Domain summary даёт список доменных отказов и того, кто на них реагирует. Persistence summary даёт точки сбоя, частичные состояния и источники повторного выполнения — их заново не ищи.

**Без отчётов** — определи код под ревью сам: diff или названные файлы плюс один шаг по графу вызовов; модуль целиком плюс один шаг наружу; весь репозиторий — только если сказано явно.

**Особенность этого skill.** Обработчик ошибки почти никогда не лежит рядом с местом её возникновения. Поэтому на Step 2 обработчики ищутся по всему репозиторию: global exception handler, error middleware, обёртка вокруг обработчика очереди, `recover` на верхнем уровне, supervisor, hook process-уровня (`unhandledRejection`, `uncaughtException`, `panic` handler). Найденный так модуль **не** становится кодом под ревью: в нём проверяется только одно — что он делает с пришедшей ошибкой. Всё остальное в нём не оценивается.

**Контекст, который нужен только этому skill**, в порядке надёжности источников:

1. **Политики повторов** — retry в HTTP- и gRPC-клиентах, настройки очереди (max attempts, dead-letter, visibility timeout), retry в jobs, backoff в библиотеке или в конфигурации. Источники: конфигурация клиентов и очередей, манифесты, документация provider.
2. **Global handlers и middleware** — что перехватывает ошибку, не дошедшую до явного обработчика: exception filter, error middleware, обёртка роутера, обработчик на уровне процесса, supervisor. Источники: точка входа приложения, регистрация middleware, конфигурация framework.
3. **Контракт ошибок наружу** — какой ответ обещан клиенту: OpenAPI и схемы ответов, `docs/`, общий тип ошибки в ответах, существующие коды. Источники: спецификация API, тесты на ответы, README.
4. **Источники повторов** — из Persistence summary, если отчёт есть; иначе очереди с at-least-once delivery, webhook providers, jobs по расписанию.

Итог — список «известно / не известно»:

```text
Известно:    очередь повторяет сообщение до 5 раз, дальше dead-letter — infra/queue.yaml
Известно:    global exception filter отвечает 500 на всё неопознанное — src/main.ts:18
Известно:    контракт ответа об ошибке: { code, message } — docs/openapi.yaml
Не известно: retry в HTTP-клиенте платежей — конфигурации нет; допущение: повторов нет
Базовая единица ошибки: исключение — источник: сценарии в `src/**` бросают и ловят,
             объявленных типов ошибок в сигнатурах нет; на границе — exception filter
```

**Базовая единица ошибки** — обязательная строка итога: механизм, которым в этом проекте выражают отказ (исключение; `Result`/`Either`; typed error в объявленной сигнатуре, включая канал `E`; пара `(value, err)`; кортеж `{:error, reason}`; код возврата), и источник — где в коде это видно. Определяется по коду под ревью и соседним модулям, а не по тому, что принято в стеке. Строка не бывает «не известно»; при двух механизмах записываются оба и граница между ними. Её роль та же, что у базовой единицы зависимости в `backend-dependency-review`: не ловить идиому стека как проблему. Механизм меняет evidence и стоимость исправления, но не вердикт: проглоченная ошибка одинаково проглочена в пустом `catch`, в `_ = err` и в проигнорированном `Result`.

Не ищи дольше одного прохода: нет ответа — «не известно», в finding это допущение с Confidence не выше medium.

## Step 1 — Источники ошибок

Для каждой операции кода под ревью ответь: **чем она может закончиться, кроме успеха?** Кандидаты, каждый с местом возникновения в коде:

- **отказ по правилу предметной области** — из Domain summary или из проверки в коде: недостаточно средств, заказ уже отправлен;
- **отказ хранилища** — нарушение constraint, конфликт версий, таймаут, недоступность соединения;
- **отказ внешнего сервиса** — код ответа, таймаут, разрыв соединения, неожиданная форма ответа;
- **отказ разбора входа** — тело запроса, сообщение очереди, ответ внешнего API не той формы;
- **отказ инфраструктуры** — очередь, кэш, файловая система, конфигурация;
- **ошибка программиста** — обращение к отсутствующему полю, деление на ноль, недостижимая ветка: в таблицу попадает, если её ловит тот же обработчик, что и остальные.

Не выдумывай отказы, которых в коде не видно: операция без I/O и без проверок отказов не даёт. Отказ, который возможен только теоретически и не выражен ни вызовом, ни проверкой, в таблицу не попадает.

Итог — таблица (лимит 15 строк, дальше группируй по компоненту):

| Операция | Какие отказы возможны | Как выражены | Кто ловит |
|---|---|---|---|
| `createOrder` (`order.service.ts:20`) | недостаточно остатка; недоступна база | доменная ошибка; исключение драйвера | `order.controller.ts:12` — один `catch` |
| `chargePayment` (`payment.client.ts:14`) | 4xx отказ провайдера; таймаут | исключение HTTP-клиента | никто, до global handler |
| `publishEvent` (`bus.ts:8`) | очередь недоступна | исключение | `order.service.ts:44` — лог, продолжение |

Колонка «кто ловит» заполняется на Step 2; на Step 1 в ней допустимо «не определено».

## Step 2 — Путь ошибки

Для каждой строки Step 1 пройди путь от места возникновения до одной из трёх конечных точек:

1. **Компонент, который принимает решение** — тот, кто по этой ошибке выбирает поведение: вернуть отказ пользователю, повторить, взять запасной вариант, эскалировать. Назови его.
2. **Внешняя граница** — ответ HTTP/gRPC, сообщение в очередь, ответ CLI: ошибка покидает систему.
3. **Обрыв** — ошибка дальше не идёт: поглощена, заменена значением по умолчанию, залогирована и забыта.

Обработчики ищи по всему репозиторию (см. особенность skill в Step 0): global handler, error middleware, обёртка обработчика очереди, `recover`, supervisor, process-level hook. Найденное не расширяет код под ревью.

Для каждого шага пути запиши, что происходит с ошибкой: проброшена как есть; обёрнута — с причиной или без; преобразована в другой тип; заменена значением; поглощена. Слои — те же шесть, что у соседей: transport / application / domain / infrastructure / persistence / external service.

Итог — по одной записи на отказ:

```text
недоступна база (persistence, order.repo.ts:31)
  → order.service.ts:40  обёрнута в Error('cannot create order'), причина не приложена
  → order.controller.ts:12  catch, ответ 500
  конечная точка: внешняя граница
таймаут провайдера (external service, payment.client.ts:14)
  → не ловится нигде
  конечная точка: global handler, src/main.ts:18, ответ 500
недоступна очередь (infrastructure, bus.ts:8)
  → order.service.ts:44  log.warn, выполнение продолжается
  конечная точка: обрыв
```

Путь, который обрывается, — кандидат для Step 3. Путь, доходящий до решающего компонента или до границы, — кандидат для Step 4 и Step 6.

## Step 3 — Потери и глотание

Кандидаты — все обрывы из Step 2 плюс формы, в которых ошибка исчезает незаметно:

- **пустой обработчик** — `catch {}`, `except: pass`, `_ = err`, `if err != nil {}`, проигнорированный `Result`, отброшенный `{:error, _}`;
- **лог и продолжение** — ошибка записана и выполнение идёт дальше так, как будто шага не было;
- **замена значением** — вместо ошибки возвращается `null`, пустой список, ноль, значение по умолчанию, и вызывающий не отличает его от настоящего результата;
- **необработанный асинхронный вызов** — промис без ожидания и без обработчика, задача, запущенная и забытая, горутина без канала ошибок;
- **ошибка в callback без проброса** — обработчик получил ошибку и не сообщил её тому, кто ждёт результат;
- **`finally`, перекрывающий ошибку** — возврат или новая ошибка в блоке завершения затирают исходную;
- **подтверждение при сбое** — ack сообщения очереди, коммит offset, удаление задачи, отметка «обработано» выполняются независимо от того, чем закончилась обработка;
- **global handler без записи** — перехватывает всё и отвечает, не оставляя следа ни в логе, ни в метрике.

Finding существует только с **последствием**: что произойдёт дальше, когда операция посчиталась успешной. «Заказ создан, событие в очередь не ушло, склад резерв не сделает, и никто об этом не узнает»; «сообщение подтверждено, платёж не проведён, повторной доставки не будет». Обрыв без последствия — Non-finding с причиной: неудача необязательного шага, о котором вызывающему знать не нужно (прогрев кэша, метрика), уже описана в Existing protections как сознательное решение.

Что **не** оценивается здесь: что осталось в хранилище после сбоя — `backend-persistence-review`; где лежит код обработчика — `backend-architecture-review`.

## Step 4 — Различимость и контекст

Два вопроса к каждому отказу, дошедшему до решающего компонента или до границы.

### Сохранился ли контекст

При обёртывании проверь, что дошло вместе с новой ошибкой: исходная причина, идентификаторы операции (кто, что, какая запись), место возникновения или стек. Finding — если по итоговой ошибке нельзя понять, что случилось, **и это кому-то нужно**: оператору на границе, чтобы понять инцидент, или коду при решении о повторе. Если по итоговой ошибке решение всё равно принимается одинаково и диагностика не страдает — Non-finding с причиной.

Типовые формы потери: обёртка с новым текстом без исходной ошибки; перехват и бросок нового объекта; текст ошибки, собранный из констант без значений; преобразование ошибки в строку раньше, чем она понадобится.

### Различимы ли исходы для того, кто принимает решение

Первая ось — **домен против инфраструктуры** — нужна почти всегда: доменный отказ отдают пользователю и не повторяют, инфраструктурный повторяют или эскалируют. Если вызывающий их не различает — finding. Типовая форма: один обработчик ловит всё и отвечает одинаково; иерархия типов ошибок существует, но на границе схлопывается в один `catch → 500` — это finding по этому правилу, а не хороший знак.

Вторая ось — **внутри домена** — только если есть вызывающий, который реагирует по-разному. Если все бизнес-отказы обрабатываются одинаково (сообщение пользователю и всё), одна категория достаточна, и требовать отдельный тип на каждый отказ не нужно.

Отдельный тип ошибки оправдывается теми же вопросами, что abstraction в `backend-dependency-review`:

| Вопрос | Ответ, который оправдывает тип | Ответ, который его отменяет |
|---|---|---|
| Сколько вызывающих его различают | два и больше, каждый ведёт себя иначе | ни одного: все ветки делают одно и то же |
| Какое решение без него не принять | «повторить или отдать пользователю» | решение и так одно |
| Что он стоит | объявление рядом с существующими | новый модуль, новая иерархия, обязательное сопоставление во всех обработчиках |

Тип, на который никто не сопоставляется, — кандидат в лишнее, а не в Existing protections; записывается P3 с упрощением.

### Логирование

Оценивается только там, где оно мешает понять, что случилось: **потеря** — единственная запись об ошибке отсутствует (это Step 3), или **дубликаты** — одна ошибка пишется на каждом уровне подъёма, и в логе три записи об одном сбое с разными текстами, из-за чего непонятно, один это инцидент или три. Правило: пишет тот, кто обрабатывает. Формат записи, уровень (`warn` против `error`), структурированность, наличие correlation id как таковое — не здесь: это формат логов, «Вне scope», владелец не назначен.

## Step 5 — Retry

Разбери каждое место, где повтор **есть**, и каждое место, где повтор **ожидается**.

Природа отказа решает вердикт:

- **повторять вредно** — отказ по правилу предметной области, отклонённый вход, 4xx от внешнего сервиса, нарушение уникальности, ошибка программиста. Повтор не изменит результат, а нагрузку и задержку добавит; для операции с побочным эффектом он ещё и множит эффект. Finding.
- **повторять уместно** — таймаут, разрыв соединения, 5xx, временная недоступность, конфликт версий при оптимистичной блокировке. Отсутствие повтора там, где повтор ожидается по контексту из Step 0 (внешний сервис с известной нестабильностью, очередь с dead-letter), — кандидат; без источника из Step 0 это Non-finding с причиной «повтор только в теории».
- **неизвестная природа** — ошибка не различима (Step 4), и политика повтора применяется ко всем отказам сразу. Это тот же finding, что и неразличимость: не создавай второй, добавь политику повторов в его Evidence.

Отдельно проверь **границы повтора**: есть ли предел числа попыток, есть ли пауза между ними и растёт ли она, и не вложены ли повторы друг в друга — retry в клиенте внутри retry в сценарии внутри повторной доставки очереди даёт произведение попыток. Повтор без предела — finding P1. Отсутствие backoff — finding при подтверждённом источнике повторов из Step 0; при единичном экземпляре и без подтверждённых повторов — P3.

Что **не** оценивается здесь: безопасен ли повтор для хранилища (создаст ли дубликат записи) — `backend-persistence-review`; здесь только вопрос, стоит ли повторять и сколько. Если повтор одновременно вреден по природе ошибки и опасен для state, finding остаётся один, а на второй аспект даётся строка «Вне scope».

Существующие защиты для Existing protections: ограниченное число попыток, растущая пауза, повтор только по названному классу отказов, dead-letter, размыкатель цепи.

## Step 6 — Границы наружу и частичный отказ

### Что уходит наружу

Внешняя граница — HTTP-, gRPC-ответ, сообщение в очередь, вывод CLI, ответ webhook. Правило: **граница переводит, а не пропускает**. Кандидаты в findings:

- стек вызовов, текст ошибки хранилища, имя таблицы, запрос, имя внутреннего класса или модуля в теле ответа;
- ожидаемый отказ отдаётся как сбой: нарушение правила предметной области приходит клиенту как 500 или как «internal error», хотя это нормальный исход операции;
- сбой отдаётся как успех: ответ 200 с телом, в котором ошибка не выражена ничем, что вызывающий проверяет;
- разные исходы неразличимы за границей: и «не найдено», и «нет прав», и «база недоступна» приходят одним ответом, и вызывающий не может выбрать поведение.

Здесь **не** оценивается форма контракта ошибки и её версионирование — это API design, «Вне scope»; и не оценивается чувствительность содержимого (персональные данные, секреты в тексте) — это security, «Вне scope». Здесь оценивается только, узнаёт ли вызывающий за границей верный исход.

### Частичный отказ

Операция из нескольких шагов, часть которых выполнилась. Два симметричных случая:

- **упала на втором шаге и вернула успех** — вызывающий считает, что сделано всё; никто не повторит и не исправит;
- **вернула ошибку, хотя первый шаг зафиксирован** — вызывающий считает, что не сделано ничего, и повторяет; либо не повторяет и оставляет систему в состоянии, о котором не знает.

Finding — с тем, что вызывающий узнал, и что он из-за этого сделает. Что при этом осталось в хранилище — `backend-persistence-review`: если finding persistence-review на это состояние уже есть, здесь не повторяется, а берётся как исходная точка — оценивается только сообщение.

Существующие защиты: ответ, в котором частичный исход выражен явно; отказ, честно сообщённый вызывающему, который может повторить; преобразование доменного отказа в ожидаемый ответ на границе.

## Step 7 — Рекомендации и substitution test

Для каждого finding — минимальное изменение, порядок от дешёвого к дорогому:

1. пробросить ошибку вместо проглатывания;
2. добавить причину и идентификаторы к обёртке;
3. разделить исходы там, где на них реагируют по-разному, — тем механизмом, который в проекте базовый (Step 0);
4. изменить политику повторов: убрать повтор для невосстановимого отказа, добавить предел и паузу;
5. преобразовать ошибку на внешней границе в ответ, который выражает верный исход.

Полная иерархия типов ошибок, перевод всего кода на `Result`-типы, новая библиотека обработки ошибок не предлагаются. Новый тип ошибки оправдан только вызывающим из finding, который по нему принимает решение.

К каждой рекомендации четыре пункта:

1. **Какая проблема пути ошибки существует** — ссылка на evidence.
2. **Что из-за неё узнаёт или не узнаёт вызывающий** — сценарий.
3. **Как изменение это закрывает** — что вызывающий будет знать после и какое решение сможет принять.
4. **Какую стоимость добавляет** — обязательное сопоставление в существующих обработчиках, новый тип, больше записей в логе, больше отказов, видимых пользователю.

Если изменение дороже проблемы — «оставить как есть», источник из Context и при каком изменении вердикт поменяется: «при втором вызывающем», «при появлении повторов», «при выходе API наружу».

**Substitution test** для каждого finding перед записью в отчёт. Перепиши Problem, Failure scenario и Why it matters без названий framework, библиотек, global handler и папок. Представь тот же backend на другом стеке — как минимум на трёх из: NestJS, FastAPI, Phoenix, Go, Rust, Spring, Effect. Если finding исчезает — его не было: «пустого `catch` в Go не бывает», «здесь принято бросать исключения», «нет класса, наследующего `HttpException`» — не findings. Если меняются только Evidence, механизм и способ исправления — finding настоящий: проглоченная ошибка, неразличимые исходы и повтор невосстановимого отказа существуют в любом механизме, а выражаются пустым блоком, отброшенным `err`, проигнорированным `Result` или несопоставлённым `{:error, _}`. Не требуй, чтобы пример работал во всех семи стеках: проверяется reasoning, а не синтаксис.
